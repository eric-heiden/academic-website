Experimental systems study · ongoing improvement loop · summary

Improving the Newton MCP harness for simulation setup and tuning

Software
Newton experimental fork · live MCP hosting unmodified example scripts
Agents
Claude Opus 5.5 (Claude Code) · GPT-6 Astra (Codex), both at xhigh effort

Abstract

Does a live connection to a running Newton simulation make coding agents faster or better at setting up and tuning simulations? Over 17 iterations, the same agent (Claude Opus 5.5 or GPT-6 Astra) solved the same task once with Newton's live MCP and once by editing and rerunning scripts; a hidden verifier checked every submission, and the MCP was improved between iterations from what the transcripts showed. Across 122 pairs on 13 tasks (controller tuning, contact debugging, system identification from real-robot data, physical replays of real manipulation episodes, and building a scene or a controller from a nearly clean plate), agents with the MCP needed 0.87× the time (95% interval 0.81–0.94; faster in 77 of 121 timed pairs) and passed about as often (111 vs 115). The gain depends on the task: 0.58× on G1 tracking, where every experiment pays setup and inspection overhead, and none where thinking or heavy simulation dominates. Token use depends on the agent: GPT-6 Astra used 0.78× the input tokens, while Opus spent the saved time on more experiments (cost 1.02×). Live use also exposed 13 Newton bugs, now reported upstream with fixes. The next phase tests whether a harness of distilled simulation-debugging knowledge (Debug Cards) plus the MCP lets cheaper models match expensive ones.

Every detail of the loop (per-iteration notes, figures, and all trials) is in the full development log. Completed studies remain available unchanged: the registered visual-calibration study (v3), the three-way study with IPython and measured Panda identification (v2), and the original two-way study.

1. How the study works

Newton's live MCP hosts an unmodified Newton example script in a running Python session. A coding agent drives it with two tools: newton_execute runs Python cells against the live simulation (with helpers such as rollout(), checkpoint(), and contact reports), and newton_rebuild reloads the script after the agent edits it.

Each trial gives a coding agent a task in a sandboxed workspace with a fixed time budget. In a pair, the same agent (Claude Opus 5.5 in Claude Code, or GPT-6 Astra in Codex) solves the same task once with the MCP and once by editing and rerunning scripts. Both start from the same compiled kernels and the same prompt apart from the workflow paragraph, and every submission is verified in a fresh process by a hidden verifier. After each iteration the transcripts are mined for friction, the harness is changed, and the next iteration measures the new version. From iteration 12 on, trials run one at a time.

The tasks grew from tuning existing scenes to working from real-robot data and, most recently, starting from a nearly clean plate.

3. What we learned

  1. The MCP saves time, and the saving comes from the live session itself. Over 121 timed pairs agents with the MCP needed 0.87× the time and passed about as often (111 vs 115 of 122). Transcript analyses trace the saving to not paying startup, scene loading, and compilation for every experiment, and to inspecting the running simulation instead of re-running it. Specialized MCP helpers contributed little.
  2. The task decides how much it saves. The MCP helped most where each experiment is cheap but has overhead: G1 tracking (0.58×), cube-toss calibration (0.76×), and the hard G1 clips (0.77×). It did not help where thinking or heavy simulation dominates: the grasp fix (1.00×), the scene from photos (1.04×), SDF grinding (1.06×), and the screwdriver replay (1.19×).
  3. Tokens and cost depend on the agent. GPT-6 Astra turned the faster loop into fewer tokens (0.78× input tokens). Opus used the time for more experiments (1.18× input tokens, cost 1.02×).
  4. Agents reach a solution sooner with the MCP but do not stop. From iteration 16 the harness verifies workspace snapshots, which measures when each run first passed. In iteration 17 the MCP runs passed first in 6 of 7 pairs (0.68× the time; pooled with iteration 16, 0.85× over 16 pairs), yet total time was 1.07×: agents kept polishing and stress-testing after they passed, more so with the live loop. Three of the three tray failures in iterations 16–17 were MCP runs that kept tuning a constraint they could not see until they crossed it.
  5. Harness details matter as much as features. How tools are advertised and loaded, and how long their results are, moved input tokens from 1.30× (h0) to 0.74× (h3). Agents without a clock stopped after a fifth to a quarter of their budget until both prompts stated the start time (h7). Idle background workers that the prompt never mentioned cost about 2 minutes over the four MCP trials of iteration 15's first half until they started on demand (h16).
  6. Agents want numbers and batches, not pictures. In iterations 0–14, newton_execute made up 88% of MCP calls and rollout() was the most used helper. Given a numeric score, agents rarely looked at renders, and image comparison, filmstrips, and an RTX or Blender backend went almost unused. Instead agents wrote their own copies of the verifier and their own multi-world batch harnesses in most recent trials, which is what the next MCP version targets. The MCP's batch helpers added in h17 went unused, but Newton's own BatchRollout, named in both prompts' docs line, became the planning engine of most Opus G1 controllers in both conditions.
  7. Frontier agents can build scenes and controllers from scratch. Both agents rebuilt the fruit-bowl scene from photos and logs and wrote model-predictive controllers (GPU sampling MPC with 512 parallel robot copies, or iLQR) that track humanoid motions, including unseen clips, within 90 minutes. Without the MCP they passed the scene task in all 10 runs, with it in 7.
  8. Verifiers need as much scrutiny as the harness. A G1 verifier changed the playback rate after construction, and the scene verifier measured the tray against a too-small outline, scored the low-friction control by a point that rises when a pear tips over in place, and scanned helper files the submission never imports. Each fix was applied to every trial of the task afterwards; re-verification changed 6 scene-task verdicts from fail to pass.
  9. A live simulator is a good bug finder. Live editing and recapture exercise code paths that one-shot scripts do not; the study found 13 Newton bugs (Section 4).

9. Cheaper models with a Debug-Card harness (running)

Can a cheaper model with a harness reach a verified solution faster and more cheaply than an expensive model working alone? Text2Sim reports that an older, cheaper model with a structured harness and distilled “Debug Cards” (symptom → likely causes → checks → repairs) beat a newer frontier model. This phase tests the same idea for Newton, with the live MCP as part of the harness.

Debug Cards. One reader per task family went through all 245 transcripts of iterations 0–17 for episodes where agents struggled. The episodes were merged into 35 cards: contacts and friction, actuators and control, edits and multi-world batches, fitting models to data, scene building and cameras, plus one card that maps error and warning messages to cards. A verifier checked every API name, default and message against the current tree, with small CPU reproductions, and corrected 23 cards. Cards hold general Newton knowledge only: no task values and no verifier details. They are installed in the workspace as an agent skill, which both CLIs discover. Inside a live MCP session, cells can search them with cards('query'), and the host names a matching card once when a reply contains a message the card explains (20 cards have such signatures).

Procedure. A task-agnostic procedure is appended to the prompt:

  1. Write a criteria checklist.
  2. Write a local check that runs the deliverable as verification will and covers each stated variation.
  3. Look up the matching card before reading Newton source.
  4. Change one thing at a time, and batch candidates where possible.
  5. After three experiments without progress, decompose the problem.
  6. Save every passing version.
  7. Stop once all criteria pass with margin.
It follows from the transcripts. 15 of the 18 real failures in iterations 0–17 came from checking something other than the stated criteria, and polishing after a pass was the largest time sink.

Tasks. There are six 30-minute tasks: G1 tracking, the hard G1 clips (budget cut from 60 to 30 minutes, which 17 of 18 earlier passes met), grasp drift, cube toss, ABC arm identification, and SDF grinding. SDF grinding is held out: no card was mined from its transcripts. The other five are in-distribution for the cards, which is a caveat for their results. Baseline B (2026-10-10). Opus and Astra without the MCP or cards passed all 12 trials (6 tasks × 2 models). The median trial took 8.1 minutes, the first passing snapshot came at a median of 4 minutes, and the median cost was $1.82. This is the bar for the cheap models.

Harness v6.1 (cards-v1): 6 of 12, at a fraction of the cost. Haiku and Luna with the MCP, the 35 cards and the procedure did as well as B on G1 tracking and grasp drift:

  • first passes at 2–12 minutes;
  • median cost $0.68 and $0.21 per trial, against B's $2.21 and $1.71;
  • Luna passed grasp drift for $0.05.
Luna also passed the held-out SDF grinding task ($0.08) and the ABC arm identification, the latter near the time limit. The cheap models failed both cube-toss calibrations, the ABC arm for Haiku, and both hard G1 runs. The traces show why:
  • Haiku ignored the cards in 3 of 6 trials and wrote measurement code it never tested. On G1 tracking it believed a passing controller still failed. On SDF grinding it reported “material removal confirmed” while nothing reached the collision geometry, which is the problem card BLD-05 describes. It finished two failing trials with more than half the time left.
  • Luna followed the procedure and read 1–12 cards per trial, but it used a fresh process for every experiment. It built new mechanisms (a balance controller, a different solver) before sweeping the existing parameters widely. On cube toss it tuned on all provided tosses down to the fourth digit and missed the held-out tosses by 0.16%. Opus solved the same task in 4 minutes by raising contact damping and validating on half the tosses.

Cheap models alone (C): Luna is already close to B. Without the MCP, the cards or the procedure:

  • Luna passed 5 of 6 tasks for a median of $0.08 per trial, with first passes at a median of 4 minutes, as fast as B. On cube toss it found the decisive contact damping and friction in 4 minutes for $0.04, much as Opus did.
  • Haiku passed 2 of 6 (G1 tracking and grasp drift).
  • Neither model passed the hard G1 clips, which both expensive models solved.

Harness v6.2 (cards-v2): same pass rate as plain Luna, but slower. The changes from v6.1:

  • The prompt lists the cards by title and asks for the matching cards before the first experiment.
  • Metric code goes into one module, tested on a case with a known answer.
  • When verification uses unseen cases, the agent tunes on part of the data and checks on the rest.
  • Experiments run in-process; parameters are swept widely before any new mechanism.
  • The agent does not finish while a criterion fails.
  • CON-02 covers overdamped impacts, and a new card, FIT-05, covers held-out failures.
Luna then passed 5 of 6 tasks (cube toss now included), but each pass came later than without any harness: G1 tracking 22 against 9 minutes, cube toss 20 against 4. On cube toss the trace shows where the time went:
  • about 2 minutes on the mandated checklist, metric module and check script;
  • rebuilding with BatchRollout an evaluation the task already provided, including a time-step bug;
  • a detour into torsional friction prompted by a solver warning and the card it attached.
For a capable cheap model the structure costs more than it returns on these tasks. Haiku again passed 2 of 6, as with cards-v1 and without any harness, but different tasks: it now passed cube toss (3.6 minutes, $0.18) and failed grasp drift. Its failures share one pattern. It reports checks that it did not run, or measured wrongly: “0.00 mm displacement, both tests pass” for a grasp that the verifier measured slipping 26 mm, after inventing a root cause the cards do not mention. For Haiku, instructions to test its own measurement did not change this. (The first attempt of these six trials failed to start: the login expired mid-iteration, because a trial's token refresh had made the copied credentials stale. The harness now returns refreshed credentials and counts such runs as infrastructure failures.)

v6.3: lite harness against the MCP alone. The lite harness has the card list, the live card helpers and four rules, with no mandatory files. Luna passed 5 of 6 with it, and with the MCP alone. Summed over the five tasks Luna can solve, the minutes to the first passing snapshot were:

  • plain: 29
  • lite harness: 34
  • MCP alone: 51
  • cards-v2: 54
  • B: 29, at 15–30 times the cost
The lite harness removed most of v6.2's overhead, but neither the cards nor the MCP made Luna faster than without them. The MCP alone slowed it on the two identification tasks. On cube toss, the live session's batch helper refused the hosted 400-world scene (it needs a one-world scene), so Luna rebuilt the evaluation with BatchRollout and lost time to a time-step bug. On the ABC arm it simply searched longer, finding partial gravity compensation after 20 minutes. Haiku passed 2 of 6 with the lite harness and none with the MCP alone. Its pass count has not moved above 2 in any arm.

What the agents used. Luna read cards in 17 of 18 harness trials, about six cards per trial, nearly always as files with the shell; the live cards() search was used once in 36 trials. Haiku opened a card in 8 of 18. The host attached 11 cards automatically, mostly the message card MSG-01 and CON-05, the latter after a solver warning about inactive torsional friction; that sent one agent on a detour. Seven of the 36 cards were never touched. Reading the card that names a task's actual cause went with passing: on grasp drift, CON-01 (priority rules) was read in 4 trials, all of which passed, against 1 of 2 without it. On G1 tracking CTL-02 shows the same 4 of 4 against 1 of 2. On SDF grinding, BLD-05 was read in 2 trials, both passes, against 1 of 4. These counts are confounded by model, because Luna reads cards and Haiku mostly does not.

Plateau for Luna and Haiku. By the protocol's stopping rule (two harness iterations without a gain over the plain arm), the harness has plateaued for the two cheapest models. Luna is as good without it, and Haiku does not rise above 2 of 6 with or without it.

v6.4: GPT-6 Sol and the expensive models with the lite harness. All 24 trials passed.

  • Sol (a fifth of Astra's price) passed all six tasks both plain and with the lite harness and the MCP, including the hard G1 clips that no cheaper arm had passed. With the harness, its first passes summed to 26 minutes against 30 without, its cost up to the first pass was $2.85 against $4.66 over the six tasks, and its median trial cost was $0.56 against B's $1.82. On cube toss it read FIT-04 and FIT-05 and passed in 4 minutes, against 10 without. This is the Text2Sim pattern: a mid-tier model with the harness reaches about the frontier model's speed (plain Astra's first passes sum to 24 minutes) at a quarter of the cost.
  • Opus and Astra with the lite harness and the MCP (E) passed 12 of 12. Against B, the first passing snapshot came sooner in 7 pairs, later in 1, and at the same 2-minute snapshot in 4. Summed over the tasks, first passes took 0.49× B's time for Opus and 0.74× for Astra, and total time 0.66× and 0.72×. Astra's cost fell to 0.63×. Opus never opened a card (only attached ones arrived), so its gain comes from the MCP and the four rules. Astra read cards in 5 of 6 trials.
Caveat: B ran a day earlier on an earlier commit, and there is one trial per cell. v6.5, now queued, runs B, B with the MCP alone, E, and Sol plain and with the harness side by side on one commit, interleaved per task, to separate the MCP's share from the cards' and to replicate the comparison.

5. Newton fixes from the study

Live use of the simulator surfaced Newton bugs that one-shot scripts rarely hit. Re-recording a CUDA graph around a warm SolverMuJoCo corrupted memory; the fix is upstream as newton#4377.

Thirteen more issues came out of the trials and the task building (#4445–#4457). Among them: MJCF bodies attached without a joint collided with their own parent and jammed a gripper; MJCF floors became invisible next to visual meshes; the camera sensor skipped convex hulls and the back of cloth; heightfields rendered with holes; ViewerRTX failed with the current ovrtx release. Ten pull requests with regression tests (#4458–#4467) fix ten of them; the cloth and texture-transform fixes for SensorCamera are merged, and the ViewerRTX fix was superseded by upstream's OVRTX update.

6. Current MCP and next steps

Current MCP (h16). Two tools. newton_execute runs Python cells against the live simulation with helpers for rollouts, checkpoints, resets, contact and solver-parameter reports, health checks, observations, and background workers; a failed cell rolls the simulation back. newton_rebuild reloads the edited script, optionally with overrides of its constants, and keeps the previous scene if the rebuild fails. Newton utilities named in both conditions' prompts: a headless runner, solver and health reports, per-world edits by label (WorldView), a Newton↔MuJoCo state bridge, camera projection, and label lookup.

Next. The cheaper-model study in section 4. If cheaper models with the harness and the MCP match the expensive ones, the useful parts of the cards go upstream as Newton documentation, and the card hooks go into the MCP.

7. Limits

  • Two models and one or two runs per cell in most iterations: single pairs vary as much as the MCP effect on some tasks. Iteration 16 runs three replicates per cell.
  • Pass rates are near the ceiling on most tasks, so the comparison mostly measures time, tokens, and cost.
  • Each iteration changes the harness, so iterations are not replicates of each other; the pooled ratio mixes harness versions and tasks.
  • Verifier fixes during an iteration are applied to every trial of the task afterwards (re-verification), but a verifier can still be wrong in ways nobody noticed.
  • One machine with one shared GPU slice; heavy simulation in both conditions can contend for it.
