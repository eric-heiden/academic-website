Experimental systems study · fourth iteration · in progress

Improving the Newton MCP harness for simulation setup and tuning

Software
Newton experimental fork · live MCP hosting unmodified example scripts
Agents
Claude Opus 5.5 (Claude Code) · GPT-6 Astra (Codex), both at xhigh effort

Abstract

Can Newton's live MCP harness be tuned until agents set up and tune simulations more efficiently with it than without it? This page tracks an ongoing improvement loop on seven tasks, six drawn from earlier reports and one from a real-robot dataset. They cover tuning humanoid controllers (including a hard clip that plain gain tuning cannot pass), fixing a grasp that slips, calibrating models against real-robot data (a DFKI double pendulum and 570 real cube tosses), adding a material-removal capability to an SDF grinding scene, and modeling a real bimanual robot station from its camera frames (ABC dataset). Each iteration runs Claude Opus 5.5 and GPT-6 Astra in concurrent pairs. The same agent solves the same task either with the live MCP or by editing and rerunning scripts, and every submission is verified in a fresh process. The transcripts are then mined for friction, and the harness is changed. After nine harness versions and 72 pairs, the loop has turned the MCP from a token cost (1.19× input tokens with h1) into a time and token saving. Across all pairs the MCP was faster in 49 (time ratio 0.83, 95% interval 0.75–0.91), and GPT-6 Astra used fewer tokens in 25 of 31 (0.70×). In iteration 7 the MCP was faster in all six pairs (0.64×). The hard humanoid task briefly separated success rates. Opus passed one of two runs with the MCP and none without, because three of those four runs quit after about 12 of their 60 minutes, believing time was up. Once h7 reported the remaining budget in MCP results and both prompts stated the start time, Opus passed all twelve runs across both conditions, finishing about a third faster with the MCP (1,039 s vs 1,559 s on average) at similar cost ($4.53 vs $4.21), because the faster live loop let it take more turns. The loop also found five ways results could silently mislead. In the live session, resets reverted the agent's own settings, quick edits could reload stale bytecode, and re-recording a CUDA graph around an already-captured MuJoCo solver corrupted memory; the last was a Newton bug, now fixed in newton-physics/newton#4377. In the study itself, the agents' sense of time was wrong, and a G1 verifier penalized controllers that precompute their plan (all G1 submissions have been re-verified). A new phase models a real robot station from its camera frames. There, every agent passed with and without the MCP, all of them fitted against the task's own image score rather than looking at screenshots, and a tuned Blender render matched the real frames about as well as the tuned ray-cast sensor (18.6 vs 18.2 dB color PSNR, with slightly lower structural scores).

Completed studies remain available unchanged: the registered visual-calibration study (v3), the three-way study with IPython and measured Panda identification (v2), and the original two-way study.

1. The improvement loop

The previous study showed that a live MCP makes photo-based calibration cheaper in tokens. This loop asks a broader question. Can the harness be tuned until it reliably helps on the setup and tuning work that earlier coding agents often failed at? The three tasks are rebuilt from earlier reports. One tunes a controller for reference-motion following (from the G1 whole-body-control report). One debugs a slipping grasp (from grasp-shake-drift and FeatherPGS). One calibrates a model against measurements from a real robot.

Each task starts from a runnable Newton example script with a realistic defect, together with a goal checked by a hidden verifier. The same agent (Claude Opus 5.5 in Claude Code, or GPT-6 Astra in Codex, both at xhigh effort) receives the same task in two conditions. In the MCP condition the script is already running live under python -m newton.mcp host. The agent can execute Python inside it, observe it, and reload the edited file, and it keeps its shell. In the no-MCP baseline it edits files and reruns scripts, so every run starts a fresh simulator process. Both trials of a pair start together on the same machine and get a 30-minute budget.

One iteration runs the pairs, reads the transcripts for friction (wasted turns, errors, source-code spelunking, redundant checks), and changes the harness. The change is committed as a new harness version, and the next iteration reruns the pairs. We report success, elapsed time (split into model and tool time), input and output tokens, API cost, and tool calls. Paired ratios below 1 favor the MCP.

2. MCP versus no MCP, per iteration

Across 72 completed pairs, the MCP reduced elapsed time (geometric-mean ratio 0.83, 95% interval 0.75–0.91; faster in 49 pairs) and input tokens (0.91, 0.79–1.04; fewer in 41 pairs). Opus's API cost was 0.99× overall; GPT-6 Astra used fewer tokens in 25 of its 31 pairs (0.70×, 0.57–0.84). Of 144 verified trials, 141 passed; the three failures are all iteration-6 Opus runs on the hard humanoid task.

The harness iterations moved these numbers. With h1, the MCP cost more tokens (1.19×) and saved little time (0.94×). h2 made it much cheaper for GPT-6 Astra (0.57× tokens, 0.69× time) but more expensive for Opus (1.63× tokens) through a tool-loading setting; h3 fixed that. With h3 (12 pairs, including second Opus replicates), the MCP was faster in 9 (0.76×, 0.60–0.94) and used fewer tokens in 8 (0.74×). With h4 (10 pairs, now including the grinding task), it was faster (0.80×), used fewer tokens (0.81×), and cut Opus's API cost to 0.78×. On G1 tracking, Opus took 220 s and $0.59 instead of 639 s and $1.16, and Astra 278 s and 0.44M tokens instead of 681 s and 1.7M. On grasp drift, Opus took 405 s and $1.20 instead of 698 s and $2.04.

The MCP did not win everywhere. On the SDF grinding task both conditions finished in about five minutes at similar cost. Astra's iteration-4 cube-toss MCP run used more tokens (2.3M vs 1.5M) after it broke its live session with the MuJoCo capture bug and spent turns restarting the host by hand, which drove the h5 changes. Iteration 5 (h5, 10 pairs) came out close to parity: 0.97× time and 0.94× tokens. Astra still saved tokens (0.71×), with G1 tracking at 273 s instead of 619 s. Opus's ratio rose to 1.24×, mainly because of two runs. In one grasp run, 900 of its 1,466 s went to a shell loop waiting on its own background fresh-process check (the MCP calls took 207 s). In one grinding run it chose more self-verification calls. Neither is a harness defect, but together they show how one agent-side detour can swing a five-pair iteration. Iteration 6 (h6) is running with two replicates of the harder humanoid task.

The hard humanoid task (iteration 6, h6). Gating the high5 clip changed the picture. GPT-6 Astra passed all four runs, with and without the MCP. Each time it wrote a whole-body inverse-dynamics balance controller from scratch, and it was faster and cheaper with the MCP in the first replicate (508 s and 0.9M tokens vs 719 s and 1.9M). Opus passed one of two runs with the MCP (root RMSE 3.3 cm, just inside the limit) and neither without it. The transcripts show why the Opus runs failed: they did not run out of ideas, but judged that their time was up. Three of the four Opus runs stopped after 11–16 minutes of a 60-minute budget, saying “I'm out of time to crack high5” or “Time's nearly up”; the one success also believed only ten minutes were left at minute 12. Agents see no wall clock, and a turn-heavy search seems to feel long to them. On the other iteration-6 tasks the MCP was faster or equal for both agents, and Astra's cube-toss run took 357 s and 0.54M tokens instead of 656 s and 2.5M.

Iteration 7 (h7): a clock for the agent. With the remaining budget in every MCP result and the start time in both prompts, all six pairs passed, and the MCP was faster in every one (0.64×, 0.51–0.80). On the hard humanoid task, Opus passed all three runs in both conditions. With the MCP it finished in 903–1,089 s; without it, in 1,370–1,669 s. Its token use and API cost were similar ($4.47 vs $4.18 per run on average), because the MCP runs used the time they now knew they had for more live experiments (up to 85 tool calls). Without the MCP, the agent now checked date -u and also kept working. Iteration-6's success gap therefore measured time awareness, not the MCP. On the other iteration-7 pairs, Opus's cube toss took 246 s and $0.44 instead of 611 s and $0.78, and Astra's grasp 229 s and 0.45M tokens instead of 388 s and 1.1M.

Verifier correction. Three iteration-7 hard-task runs first failed only on the unseen slower playback, with the robot upright but a joint RMSE of 0.14 rad. The G1 verifiers produced that playback by lowering motion.fps on an already-built example, so controllers that precompute a plan from their input clip (which the task allows) kept tracking a stale 30 fps plan. The verifiers now pass the time-scaled clip as an ordinary file through --motion. All 40 G1 submissions from every iteration were re-verified. Exactly those three changed (all to pass), and every other outcome, including the iteration-6 failures, stayed the same. The tables report the re-verified results.

Iteration 8 (h8). All eight pairs passed, and the MCP was faster in six (0.80×, 0.65–0.95), but Opus used more tokens (1.21×). Across the six hard-task pairs that ran with a clock (iterations 7–8), Opus passed every run in both conditions. With the MCP it averaged 1,039 s against 1,559 s, using 6.1M against 5.2M input tokens ($4.53 vs $4.21). The live loop makes each experiment cheaper in time, so Opus runs more of them: 54–87 tool calls with the MCP against 42–75 without. The visible clock has a similar side effect on easy tasks. After passing G1 tracking, one Opus MCP run noted “With time left, I'm briefly looking at why high5 falls (it's optional)” and spent 2.2M tokens against 0.9M without the MCP. The best real-robot model of the loop also came from an iteration-8 MCP run, at 0.092 rad on the 75 s held-out pendulum recording (the reference fit reached 0.131 rad).

Iteration 9 (h9): a real scene. All eight ABC station-twin runs passed, most with a wide margin (edge correlation 0.71–0.78, SSIM 0.68–0.71, color PSNR 19.2–20.4 dB against limits of 0.67, 0.64, and 17 dB), so the task does not separate the conditions. Time was mixed (0.86× overall): Opus took 796 s with the MCP and 1,540 s without in the first replicate, but 1,060 s and 749 s in the second, and Astra 1,841 s and 1,354 s, then 647 s and 1,154 s. The clearer signal is time to a first passing score on the given frames: Opus reached it after 401 s with the MCP and 1,131 s without; the restart run spent 600 s in a single camera-fit script, while the MCP run's longest fitting call took 40 s. Astra reached it at about the same time in both conditions (589 s and 646 s) and then kept refining for another 20 minutes with the MCP. Opus paid 1.35× more with the MCP, in more turns.

3. What each iteration changed

Each version is a commit on the Newton branch eric-heiden/newton-live-mcp, driven by what the previous iteration's transcripts showed.

h0 → h1. Iteration-0 agents wrote the same frame-by-frame evaluation loops in almost every call. They grepped the MuJoCo solver source to learn which contact parameters were in effect, and a missing import newton invalidated the scene. h1 added rollout(), solver_contacts(), health(), a preloaded newton, and non-invalidating errors for hosted scripts. It also added automatic CUDA-graph recapture after live attribute edits, and compiling reloaded scripts from source; a regression test had shown that a script edited within the same second could reload stale bytecode. Correction: an earlier version of this page said an iteration-0 agent's live shake-amplitude edit was silently ignored because it was baked into a captured graph. That was wrong: the example passes the amplitude to a kernel launched outside its graphs, so the edit took effect.

h1 → h2. In iteration 1, Astra's first call to solver_contacts() found the grasp's root cause directly: the fingers' higher geom priority imposes a soft material with a 0.2 s solref time constant on the cube. Opus still read solver source for the same fact; in h1 the helper was listed only in the server instructions, not in the task's host guide. MCP tool results were smaller than the no-MCP shell output (72k vs 110k characters on grasp drift), so the token overhead had to come from elsewhere. It came from about 2.4k tokens of tool schemas and instructions resent on every turn, and from about 10% more turns. h2 advertises only newton_execute and newton_rebuild with short instructions (about 0.8k tokens), names the deciding material in the contact report, lists the helpers in the host guide, and hosts two worker copies of the scene for parallel or background sweeps. To skip the tool-search round trip, it also set ENABLE_TOOL_SEARCH=false.

h2 → h3. Iteration 2 exposed three problems. (1) ENABLE_TOOL_SEARCH=false loads the schemas of every deferred built-in Claude Code tool, not just Newton's: Opus MCP trials started at 30k tokens instead of 15k. h3 marks only the Newton server alwaysLoad, which gives 14.9k with no tool-search round trip. (2) Checkpoints and resets restored every scalar attribute of the hosted example, so a look-ahead or gain the agent set before rollout(start=True) was silently reverted, and one sweep returned identical rows. h3 rewinds only the scalars that step() itself advances. (3) An Opus grasp session crashed with CUDA error 700 after live solver experiments. Reproducing it showed that h1's recapture was unsafe. Newton examples capture a graph around the solver's first step, and SolverMuJoCo allocates buffers during that step, so those buffers belong to the first graph. Recording a second graph around the same solver either segfaults or silently corrupts the simulation (a grasped cube ended 99 m below the table). A one-box scene fails the same way, and one eager step before the first capture avoids it. h3 recaptures only when example.solver has been replaced, which is safe. For other changes it reports that values inside the captured graphs keep their old values until a rebuild. recapture() refuses to run around the same solver. The grasp and G1 MCP trials of iterations 1 and 2 hit such recaptures (for example 10 times in the i2 Opus grasp trial). Their live numbers may have been corrupted, although their verified submissions were not affected.

h3 → h4. With h3, the MCP's first turn was still 2.5k tokens larger than the no-MCP baseline's. Part of that came from the host guide appearing twice: once in the task prompt and again in the server instructions. h4 adds --no-app-guide to the stdio bridge, and the harness uses it because its prompts carry the guide. Hosting was also extended to kinematic examples without a dynamics solver or second state (such as the grinding scene), and the host guide now says that non-array objects such as SDFs are not rewound by reset.

h4 → h5. Iteration 4 exposed three gaps. (1) Hosted examples run with a null viewer, so geometry an example draws itself in render(), such as the ground workpiece surface, was invisible to observe, and an agent plotted it with matplotlib instead. The host's viewer now records log_mesh calls, and color observations composite those meshes over the model's shapes by depth; auto-framing uses mesh bounds. (2) The MuJoCo capture bug struck again through ordinary task code. Astra called the task's own rollout() on the example's already-captured solver, and the live process could no longer allocate memory. An eager step on scratch states followed by solver.reset() prevents this even in the minimal repro, so the host process now warms every SolverMuJoCo this way; physics is unchanged (the grasp scene matches to seven digits). (3) With the CUDA context broken, the agent had to restart the host by hand. newton_rebuild(arguments={"restart": true}) now re-executes the host process, and the MCP client re-reads the connection file and retries when its server restarts. The host guide also recommends workers.map over submit for sweeps, because polling a future had cost an extra turn per sweep.

h5 → h6. The MuJoCo capture bug is now fixed where it originated. newton-physics/newton#4377 creates the solver's inverse shape mapping at construction instead of lazily inside the first (usually captured) step, with tests for discarded, retained, and replayed graphs. The loop branch merges that fix, drops the host's eager warm-up workaround, and goes back to re-recording an example's CUDA graphs after any cell that edits example attributes. As a result, kernel arguments baked into graphs pick up live changes again. With the fix, every earlier failing scenario (the one-box repro, and the grasp scene with its old graph dropped, retained, or replayed) now runs correctly.

h6 → h7. Because Opus misjudged elapsed time on the hard task, h7 gives MCP sessions a deadline (--deadline on the host, set by the harness to the trial budget), and every status in a tool result then includes time_left_s. To keep the comparison fair, both conditions' prompts now also state the task's UTC start time, so a script-only agent can check the clock with date; the MCP only makes the remaining time passive and ever-present.

h7 → h8. Profiling the long hard-task transcripts showed that newton_rebuild returned the full describe payload (application guide, operation list, limits; about 4.6k characters). One Opus run rebuilt 14 times, adding 65k characters that stayed in context for every later turn. Rebuild now returns a compact status of about 180 characters. h8 also carries the corrected G1 verifiers.

4. Real-robot calibration data

The system-identification task uses public measurements from the DFKI underactuated double pendulum (BSD-3-Clause). The robot has two quasi-direct-drive AK80-6 motors with 6:1 gearing, a 0.2 m first link, and a 0.3 m second link. Its fourteen design C.0 system-identification runs record measured joint angles, velocities, and motor torques. Runs 00–09 are given to the agent, while runs 10 (20 s excitation) and 11 (75 s, full swings, 300 Hz) are held out. The model replicates one pendulum per evaluation window as a separate Newton world, so a whole recording is evaluated in one batched SolverMuJoCo rollout (about 0.5 s on the study GPU).

The thresholds were set before any agent trial, from three reference parameter sets. The nominal starter misses badly. The published DFKI identification, mapped to a physically valid Newton model, roughly halves the error but does not pass. A direct Nelder–Mead fit of all twelve Newton parameters to runs 07–09 passes with margin. So the gates reward calibrating the simulator itself, beyond copying published numbers.

The agents solved this task quickly and in the same way in both conditions. They fitted the identifiable base parameters by linear least squares on inverse dynamics, then refined them with their own NumPy (Opus) or C++ (Astra) forward models under the multiple-shooting objective, and used Newton only to confirm. On a two-link system the simulator is not needed in the inner loop, so the live MCP has little to offer here. Its value should show on systems where the simulator is the only practical forward model, with contact or many degrees of freedom.

From iteration 3 a second real dataset is used where the simulator is the practical forward model: the ContactNets cube tosses (BSD-3-Clause), 570 hand tosses of an acrylic cube onto a wooden table tracked at 148 Hz (Pfrommer et al., CoRL 2020). The cube's size, mass, and inertia are measured and fixed. The agent calibrates contact behavior (friction, stiffness, damping, torsional friction, table height, solver settings) so that open-loop rollouts from each toss's first frame reproduce the recorded bounces, slides, and tumbles. Each toss is one Newton world, and a CUDA-graph rollout of all 400 training tosses takes about 2–4 s.

The thresholds were set before any agent trial. Published parameters do not transfer. The ContactNets friction coefficient with untuned stiffness halves the position error but leaves orientation unchanged. The MuJoCo fit of Acosta et al., mapped to Newton's contact model, is worse than friction alone, because stiffness and damping mean different things across simulators and timesteps. A Nelder–Mead fit of five Newton contact parameters on 200 training tosses passes with margin.

5. Next phase: visual fidelity and real-world scenes

The loop so far measured tasks where a simulation is judged by numbers. The next phase targets tasks where the agent must also get the look right: modeling a real scene, such as the bimanual workcells of the ABC dataset, so that renders from a calibrated camera match real video, and then tuning its behavior against the recording. That puts the MCP's images under scrutiny, since a frontier model can only dial in what it can see.

A first audit of the h8 observations found three problems beyond plain aesthetics. (1) The MJCF importer hid every collision shape of a model that also has visual meshes, including world floor planes, which have no visual twin. The Unitree G1 therefore floated on a black void in every viewer and camera sensor. (2) MuJoCo's procedural checker textures were not imported, so such floors got an arbitrary palette color. (3) SensorTiledCamera always rendered every world. The MCP had to budget world count × width × height pixels to show one world, so in the 400-world cube-toss task, any observation above about 100 × 100 pixels was refused. All three are fixed in Newton itself, with regression tests. The camera sensor gained a world_ids option that renders only selected worlds; the 400-world scene now renders a supersampled 640 × 480 view in about 20 ms.

The observations themselves now supersample color 2×2 and resolve it in linear light on the GPU. They draw a sky gradient behind the scene and a checker of a reported round cell size (for example 0.25 m) on ground planes, which gives the model scale and motion cues. They fit the camera to the scene's projected extent rather than a loose bounding sphere. observe also accepts calibrated OpenCV intrinsics (focal lengths, principal point, distortion), so renders can be compared pixel for pixel with frames from a real camera.

Two heavier renderers were evaluated. Newton's ViewerRTX (the OVRTX path tracer) had broken with ovrtx 0.5, which renamed render variables and changed its DLPack interface, and it hung whenever a DISPLAY was set without a running X server. Both are fixed. It is now an optional MCP backend: observe(backend="rtx") renders the same camera and world with 16 path-traced samples in about 1 s per frame after a one-time scene export of about 20 s, against about 20 ms for the camera sensor. Blender 4.5 (Cycles on CUDA) renders a USD export of the same scene in about 5 s per frame.

In the research round's comparisons against real ABC frames, photographic rendering alone did not bring renders measurably closer to the real images. What mattered was a look the agent can tune (camera pose, light, colors) and a number to tune against. Two changes follow from that. The camera sensor gained ambient and light-color controls, and its lighting now follows the model's up axis; Y-up scenes used to be lit from below. The MCP workspace gained render() and compare_images(), which report PSNR, SSIM, and edge correlation against a reference frame and show mismatch, edge, or blend panels. A live Blender connection does not look necessary: USD export plus an optional RTX or Blender render covers the photographic case, and it keeps the agent's loop fast.

Replaying real ABC episodes in Newton turned up more importer and renderer gaps, now fixed with tests. MJCF geoms with zero alpha, such as the camera housings, rendered as opaque black and blocked the view of a camera pulled back by a fit. MuJoCo's binary .msh meshes, which the ABC scenes use, could not be loaded.

The first ABC task, the station twin (Table 1), starts from the nominal CAD model of the YAM station (Figure 3). The agent must fit the camera mount and the enclosure (the real one is narrower and deeper than the CAD), model the bin and the seven dishes on the table, and match the colors and lighting. The verifier renders five held-out frames between the given ones through the calibrated camera, with its own copy of the renderer, and scores them against the recording. Reference solutions set the thresholds. The starter scores 0.37 edge correlation, 0.53 SSIM, and 14.0 dB color PSNR. Fitting only the camera and the enclosure reaches 0.65, 0.63, and 15.1 dB. Adding the objects with fitted colors reaches 0.72, 0.66, and 18.2 dB. Iteration 9 runs this task in pairs, and its results will appear in Table 2.

Replaying the logs also exposed the real arm's controller. The measured torques fit a PD law on the command from one frame earlier (R² 0.82–0.98 on most joints), with gains of about 74 N m/rad on the large joints, against 40 in the ABC simulation model. This became the second ABC task, arm replay (Table 1), which iteration 10 runs in pairs.

Blender as an MCP backend. The research round's Blender bridge is now an optional MCP backend. observe(backend='blender') renders with EEVEE ('blender_cycles' path-traces) through the same camera as the sensor, including calibrated intrinsics; object centroids agree with sensor renders to within 0.5 px. Newton stays the source of truth: one world is exported once to a long-running Blender process, and each render streams only shape and camera poses over a Unix socket (about 1 s per warm EEVEE frame on the shared GPU, 2–4 s at the real camera's 640 × 480 under load). A blender(code) helper runs bpy in the same process to edit materials, lights, and exposure. The backend is advertised only when Blender is installed. 6. Findings so far

Frontier agents solve these setup, tuning, and capability tasks with or without the MCP, once they know how much time they have. 141 of 144 verified trials passed. The three failures were all Opus runs on the hard humanoid task that stopped far too early. After the harness began reporting remaining time, all twelve later runs of that task passed.

Harness details decide whether the MCP saves or costs tokens. The same live session went from 1.19× input tokens (h1) to 0.74–0.81× (h3–h4) through changes in how tools are advertised and loaded, what the helpers return, and how resets behave. One setting pushed Opus to 1.63× before it was reverted. Per-turn fixed context and extra turns explain the overhead, not tool output.

The MCP reliably saves wall-clock time; whether it saves tokens depends on how the agent spends that time. Across all pairs it was faster in 49 of 72 (0.83×), and on the long hard task by about a third. GPT-6 Astra turned the faster loop into fewer tokens (0.70×). Opus tends to turn it into more experiments, especially on long or open-ended tasks (1.10× tokens overall, but 0.97× API cost thanks to prompt caching).

Agents need a clock, and a clock changes their behavior. On the one task that required a long search, Opus repeatedly stopped after 11–16 of its 60 minutes because it believed its budget was spent. Reporting the remaining time with every MCP result, and stating the start time in the prompt, fixed that in both conditions, and all twelve later runs passed. The same visibility leads agents to spend spare budget on optional goals after passing. A harness can supply the clock, but only the task can say whether the spare time is worth spending.

For modeling a real scene, a score beats a prettier picture. Given a renderer that matches the verifier and a scoring function, none of the eight station-twin runs called observe, the RTX backend, or compare_images; every agent fitted the camera, geometry, and colors in loops over the score and looked at its own composites with show(). In a controlled comparison on the same twin and frames, Blender EEVEE with tuned exposure and per-object colors reached 18.6 dB color PSNR, 0.65 SSIM, and 0.69 edge correlation, against 18.2 dB, 0.66, and 0.72 for the tuned sensor. Untuned, Blender scored 14.5 dB, and exposure alone recovered 3.9 dB. Photographic rendering helps people judge a scene, but for agents fitting to real frames the gains come from tunable look parameters and a metric.

A live session needs guards that a restart workflow gets for free. Three silent-divergence bugs surfaced only through agent use: settings reverted by reset, stale bytecode after a quick edit, and memory corruption from recapturing a CUDA graph around a warm solver. A live harness is only as trustworthy as its bookkeeping, and each fix has a regression test.

The MuJoCo capture issue was a Newton bug, now fixed at the source. SolverMuJoCo created a persistent mapping lazily inside its first step. Newton examples capture that step in a CUDA graph, and any second capture around the same solver then crashed or corrupted the simulation, on upstream main as well (repro in Section 7). newton-physics/newton#4377 creates the mapping at construction. Live tooling found this bug because it re-records graphs in ways that one-shot scripts never do.

Explaining effective solver parameters saves investigation. Where an agent used the contact report, it found the grasp's root cause (finger priority overriding the cube's material) in its first call. Agents without it read solver kernels to reconstruct the same fact.

Verifiers need the same scrutiny as the harness. A G1 verifier changed the playback rate after construction and silently failed controllers that precompute a plan. It was caught only because an agent claimed to pass all clips and the verification disagreed. Re-verifying all 40 G1 submissions changed exactly the three affected outcomes.

7. Limits

This is an exploratory loop, not a registered study. The harness changes between iterations, three to seven pairs per agent and iteration cannot separate small effects from noise, and tasks are added as the loop goes. All pairs ran on one shared 4-CPU machine with a MIG GPU slice. Concurrent pairs control for load between conditions but not across iterations, and reference fits sometimes ran during trials.

Iteration 0 has no Astra trials. One iteration-1 Astra G1 pair was excluded because the operator accidentally terminated its live host while testing workers; it was rerun with the same harness. Live results in some iteration-1 and iteration-2 MCP trials may have been corrupted by the recapture bug described in Section 3; their verified submissions were not. Codex does not report API cost. Because every task so far is solvable in both conditions, these results say nothing yet about whether the MCP raises success on harder problems. Agent-side detours, such as a shell loop waiting on the agent's own background job, can dominate a single pair's time; they are kept in all aggregates.
