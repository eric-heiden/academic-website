Experimental systems study · fourth iteration · in progress

Improving the Newton MCP harness for simulation setup and tuning

Software
Newton experimental fork · live MCP hosting unmodified example scripts
Agents
Claude Opus 5.5 (Claude Code) · GPT-6 Astra (Codex), both at xhigh effort

Abstract

Can Newton's live MCP harness be tuned until agents set up and tune simulations more efficiently with it than without it? This page tracks an ongoing improvement loop on three tasks drawn from earlier reports. The tasks are tuning a humanoid tracking controller, fixing a grasp that slips, and calibrating a model of a real double pendulum from measured torques. Each iteration runs Claude Opus 5.5 and GPT-6 Astra in concurrent pairs. The same agent solves the same task either with the live MCP or by editing and rerunning scripts. Every submission is verified in a fresh process. The transcripts are then mined for friction, and the harness is changed. After two iterations (8 pairs), both conditions solved every task. With the MCP, agents were slightly faster (time ratio 0.93) but used more input tokens (ratio 1.22, 95% interval 1.06–1.41). Opus gained most on the scenes that are slow to restart, taking 246 s instead of 531 s on G1 tracking. Astra was slower with the MCP on two of three tasks. The extra tokens do not come from tool output, which is smaller than the script workflow's shell output. They come from about 2.4k tokens of tool schemas and instructions resent on every turn, plus about 10% more turns. Iteration 2, now running, cuts that fixed context to about 0.8k tokens and adds parallel worker copies of the live scene. Earlier iterations fixed two ways live edits could silently fail. One was a shake amplitude baked into a captured CUDA graph; the other was stale bytecode after a quick script edit. They also added one-call rollouts and a contact report that names the parameters the solver actually uses.

Completed studies remain available unchanged: the registered visual-calibration study (v3), the three-way study with IPython and measured Panda identification (v2), and the original two-way study.

1. The improvement loop

The previous study showed that a live MCP makes photo-based calibration cheaper in tokens. This loop asks a broader question. Can the harness be tuned until it reliably helps on the setup and tuning work that earlier coding agents often failed at? The three tasks are rebuilt from earlier reports. One tunes a controller for reference-motion following (from the G1 whole-body-control report). One debugs a slipping grasp (from grasp-shake-drift and FeatherPGS). One calibrates a model against measurements from a real robot.

Each task starts from a runnable Newton example script with a realistic defect, together with a goal checked by a hidden verifier. The same agent (Claude Opus 5.5 in Claude Code, or GPT-6 Astra in Codex, both at xhigh effort) receives the same task in two conditions. In the MCP condition the script is already running live under python -m newton.mcp host. The agent can execute Python inside it, observe it, and reload the edited file, and it keeps its shell. In the no-MCP baseline it edits files and reruns scripts, so every run starts a fresh simulator process. Both trials of a pair start together on the same machine and get a 30-minute budget.

One iteration runs the pairs, reads the transcripts for friction (wasted turns, errors, source-code spelunking, redundant checks), and changes the harness. The change is committed as a new harness version, and the next iteration reruns the pairs. We report success, elapsed time (split into model and tool time), input and output tokens, API cost, and tool calls. Paired ratios below 1 favor the MCP.

2. MCP versus no MCP, per iteration

Every trial so far solved its task in both conditions, including tasks that earlier coding agents did not always finish. Success therefore does not separate the conditions, and efficiency does. Across the eight completed pairs, the MCP reduced elapsed time slightly (geometric-mean ratio 0.93) but increased input tokens (1.22). Output tokens and API cost were at parity. The effect depends on agent and task. Opus finished G1 tracking in 246 s with the MCP instead of 531 s, and grasp drift in 472 s instead of 631 s. On the pendulum the two conditions were tied at about 280 s. Astra was faster with the MCP on G1 (420 s vs 523 s) but slower on grasp drift (292 s vs 173 s) and on the pendulum (1,177 s vs 845 s).

Iteration 2 (harness h2) is running. Its pairs will appear here as they complete, with a second Opus replicate for each task.

3. What each iteration changed

Each version is a commit on the Newton branch eric-heiden/newton-live-mcp. Changes are driven by what the previous iteration's transcripts showed.

h0 → h1. The iteration-0 agents wrote the same frame-by-frame evaluation loops in almost every call. They grepped the MuJoCo solver source to learn which contact parameters were actually in effect. A missing import newton invalidated the scene and cost a recovery turn. Worst, one Opus agent set example.shake_amplitude = 0.1 live, but the amplitude is an argument baked into the example's captured IK graph. Its live “10 cm” tests therefore silently ran the 3 cm shake. h1 added rollout(), solver_contacts(), health(), a preloaded newton, and non-invalidating errors for hosted scripts. It also recaptures the example's CUDA graphs automatically whenever a cell changes an example attribute, and says so in the result. Writing a regression test exposed a second silent failure: reloading a script edited within the same second could run stale bytecode. The host now compiles from source.

h1 → h2. In iteration 1, Astra's first call to solver_contacts() found the grasp's root cause directly. The fingers' higher geom priority imposes a soft material with a 0.2 s solref time constant on the cube. Opus still read solver source for the same fact; in h1 the helper was listed only in the server instructions, not in the task's host guide. The token analysis showed that MCP tool results are smaller than the no-MCP shell output (72k vs 110k characters on grasp drift). The extra tokens instead come from about 2.4k tokens of tool schemas and instructions resent on every turn, and from about 10% more turns. Those turns include a tool-search round trip, a mandatory describe call, and final fresh-process checks that repeat live verification. h2 advertises only newton_execute and newton_rebuild with short instructions (about 0.8k tokens), removes the extra calls, and lists the helpers in the task's host guide. It names the deciding material in the contact report and hosts two worker copies of the scene, so sweeps can run in parallel or in the background.

4. Real-robot calibration data

The system-identification task uses public measurements from the DFKI underactuated double pendulum (BSD-3-Clause). The robot has two quasi-direct-drive AK80-6 motors with 6:1 gearing, a 0.2 m first link, and a 0.3 m second link. Its fourteen design C.0 system-identification runs record measured joint angles, velocities, and motor torques. Runs 00–09 are given to the agent, while runs 10 (20 s excitation) and 11 (75 s, full swings, 300 Hz) are held out. The model replicates one pendulum per evaluation window as a separate Newton world, so a whole recording is evaluated in one batched SolverMuJoCo rollout (about 0.5 s on the study GPU).

The thresholds were set before any agent trial, from three reference parameter sets. The nominal starter misses badly. The published DFKI identification, mapped to a physically valid Newton model, roughly halves the error but does not pass. A direct Nelder–Mead fit of all twelve Newton parameters to runs 07–09 passes with margin. So the gates reward calibrating the simulator itself, beyond copying published numbers.

The agents solved this task quickly and in the same way in both conditions. They fitted the identifiable base parameters by linear least squares on inverse dynamics, then refined them with their own NumPy (Opus) or C++ (Astra) forward models under the multiple-shooting objective, and used Newton only to confirm. On a two-link system the simulator is not needed in the inner loop, so the live MCP has little to offer here. Its value should show on systems where the simulator is the only practical forward model, with contact or many degrees of freedom.

5. Findings so far

Frontier agents now solve these setup and tuning tasks with or without the MCP. Every one of the 16 verified trials passed, so the harness has to earn its place through efficiency and reliability.

The MCP saves time where restarts are expensive and the agent works synchronously. For Opus it halved the time on G1 tracking and cut grasp drift by a quarter, but it tied on the pendulum, whose fresh runs are cheap. Astra overlaps background scripts with its reasoning in the no-MCP condition, and blocking MCP calls took that away on two of three tasks. The parallel workers in h2 are meant to restore it.

Per-turn fixed context, not tool output, drives the token overhead. Tool schemas and instructions are resent on every API call. At about 2.4k tokens over 20–40 calls, that alone accounts for most of the 20% gap. Iteration 2 tests whether trimming them closes it.

A live session needs guards that a restart workflow gets for free. Captured CUDA graphs, cached bytecode, and baked kernel arguments can make a live edit silently ineffective, which is worse than a slow restart. h1's automatic recapture and source compilation remove the two cases seen so far.

Explaining effective solver parameters saves investigation. Where an agent used the contact report, it found the grasp's root cause (finger priority overriding the cube's material) in its first call. Agents without it read solver kernels to reconstruct the same fact.

6. Limits

This is an exploratory loop, not a registered study. The harness changes between iterations, one pair per task and model is not enough to separate small effects from noise, and the task set was fixed only when the loop started. All pairs ran on one shared 4-CPU machine with a MIG GPU slice. Concurrent pairs control for load between conditions but not across iterations.

Iteration 0 has no Astra trials. One iteration-1 Astra G1 pair was excluded because the operator accidentally terminated its live host while testing workers, and it was rerun with the same harness. Codex does not report API cost. Because every task is solvable in both conditions, these results say nothing about whether the MCP raises success on harder problems.
