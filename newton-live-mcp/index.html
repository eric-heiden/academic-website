Experimental systems study · fourth iteration · in progress

Improving the Newton MCP harness for simulation setup and tuning

Software
Newton experimental fork · live MCP hosting unmodified example scripts
Agents
Claude Opus 5.5 (Claude Code) · GPT-6 Astra (Codex), both at xhigh effort

Abstract

Can Newton's live MCP harness be tuned until agents set up and tune simulations more efficiently with it than without it? This page tracks an ongoing improvement loop on five tasks drawn from earlier reports: tuning a humanoid tracking controller, fixing a grasp that slips, calibrating models against real-robot data (a DFKI double pendulum and 570 real cube tosses), and adding a material-removal capability to an SDF grinding scene. Each iteration runs Claude Opus 5.5 and GPT-6 Astra in concurrent pairs. The same agent solves the same task either with the live MCP or by editing and rerunning scripts, and every submission is verified in a fresh process. The transcripts are then mined for friction, and the harness is changed. After five harness versions and 36 pairs, both conditions have solved every task, and the loop has turned the MCP from a token cost into a consistent saving. With the h1 harness, agents used 1.19× the input tokens of the no-MCP baseline. With h3 and h4 (22 pairs), they finished in about three quarters of the time (0.76× and 0.80×), used fewer input tokens (0.74× and 0.81×), and Opus's API cost fell to 0.78× in iteration 4. Across all 36 pairs, the MCP was faster in 24 (time 0.81×, 95% interval 0.71–0.92). The loop also exposed three ways a live session could silently diverge from its script, and fixed them. Resets reverted the agent's own settings. Quick edits could reload stale bytecode. And a CUDA graph captured around an already-used MuJoCo solver corrupted memory. The last is a Newton bug that also occurs on main; the host now warms each solver with one eager step, and a broken process can be restarted from the MCP.

Completed studies remain available unchanged: the registered visual-calibration study (v3), the three-way study with IPython and measured Panda identification (v2), and the original two-way study.

1. The improvement loop

The previous study showed that a live MCP makes photo-based calibration cheaper in tokens. This loop asks a broader question. Can the harness be tuned until it reliably helps on the setup and tuning work that earlier coding agents often failed at? The three tasks are rebuilt from earlier reports. One tunes a controller for reference-motion following (from the G1 whole-body-control report). One debugs a slipping grasp (from grasp-shake-drift and FeatherPGS). One calibrates a model against measurements from a real robot.

Each task starts from a runnable Newton example script with a realistic defect, together with a goal checked by a hidden verifier. The same agent (Claude Opus 5.5 in Claude Code, or GPT-6 Astra in Codex, both at xhigh effort) receives the same task in two conditions. In the MCP condition the script is already running live under python -m newton.mcp host. The agent can execute Python inside it, observe it, and reload the edited file, and it keeps its shell. In the no-MCP baseline it edits files and reruns scripts, so every run starts a fresh simulator process. Both trials of a pair start together on the same machine and get a 30-minute budget.

One iteration runs the pairs, reads the transcripts for friction (wasted turns, errors, source-code spelunking, redundant checks), and changes the harness. The change is committed as a new harness version, and the next iteration reruns the pairs. We report success, elapsed time (split into model and tool time), input and output tokens, API cost, and tool calls. Paired ratios below 1 favor the MCP.

2. MCP versus no MCP, per iteration

Every trial so far solved its task in both conditions, so efficiency, not success, separates them. Over all 36 completed pairs, the MCP reduced elapsed time (geometric-mean ratio 0.81, 95% interval 0.71–0.92; faster in 24 pairs) and input tokens (0.89, 0.74–1.05; fewer in 20 pairs). Opus's API cost was 0.92× overall.

The harness iterations moved these numbers. With h1, the MCP cost more tokens (1.19×) and saved little time (0.94×). h2 made it much cheaper for GPT-6 Astra (0.57× tokens, 0.69× time) but more expensive for Opus (1.63× tokens) through a tool-loading setting; h3 fixed that. With h3 (12 pairs, including second Opus replicates), the MCP was faster in 9 (0.76×, 0.60–0.94) and used fewer tokens in 8 (0.74×). With h4 (10 pairs, now including the grinding task), it was faster (0.80×), used fewer tokens (0.81×), and cut Opus's API cost to 0.78×. On G1 tracking, Opus took 220 s and $0.59 instead of 639 s and $1.16, and Astra 278 s and 0.44M tokens instead of 681 s and 1.7M. On grasp drift, Opus took 405 s and $1.20 instead of 698 s and $2.04.

The MCP did not win everywhere. On the SDF grinding task both conditions finished in about five minutes at equal cost. Astra's iteration-4 cube-toss MCP run used more tokens (2.3M vs 1.5M) after it broke its live session with the MuJoCo capture bug and spent turns restarting the host by hand. That case drove the h5 changes below. Iteration 5 (harness h5) is running on all five tasks; its pairs will appear here as they complete.

Two agent results stand out beyond the harness comparison. In iteration 4, Astra without the MCP wrote a double-support inverse-dynamics balance controller for the G1 (a small QP solved with OSQP on MuJoCo's model, applying no forces to the floating base). It is the first controller in the loop that also tracks the optional hard clip, with 1.1 cm root error and the robot upright; every earlier trial fell. On the SDF grinding task, which reproduces a capability built for an earlier report, all four agents independently found that Newton's collision pipeline and surface extraction share the texture SDF. Each implemented an in-place CSG update of its coarse and fine grids within five minutes, and all removed the swept volume to within 1%.

3. What each iteration changed

Each version is a commit on the Newton branch eric-heiden/newton-live-mcp, driven by what the previous iteration's transcripts showed.

h0 → h1. Iteration-0 agents wrote the same frame-by-frame evaluation loops in almost every call. They grepped the MuJoCo solver source to learn which contact parameters were in effect, and a missing import newton invalidated the scene. h1 added rollout(), solver_contacts(), health(), a preloaded newton, and non-invalidating errors for hosted scripts. It also added automatic CUDA-graph recapture after live attribute edits, and compiling reloaded scripts from source; a regression test had shown that a script edited within the same second could reload stale bytecode. Correction: an earlier version of this page said an iteration-0 agent's live shake-amplitude edit was silently ignored because it was baked into a captured graph. That was wrong: the example passes the amplitude to a kernel launched outside its graphs, so the edit took effect.

h1 → h2. In iteration 1, Astra's first call to solver_contacts() found the grasp's root cause directly: the fingers' higher geom priority imposes a soft material with a 0.2 s solref time constant on the cube. Opus still read solver source for the same fact; in h1 the helper was listed only in the server instructions, not in the task's host guide. MCP tool results were smaller than the no-MCP shell output (72k vs 110k characters on grasp drift), so the token overhead had to come from elsewhere. It came from about 2.4k tokens of tool schemas and instructions resent on every turn, and from about 10% more turns. h2 advertises only newton_execute and newton_rebuild with short instructions (about 0.8k tokens), names the deciding material in the contact report, lists the helpers in the host guide, and hosts two worker copies of the scene for parallel or background sweeps. To skip the tool-search round trip, it also set ENABLE_TOOL_SEARCH=false.

h2 → h3. Iteration 2 exposed three problems. (1) ENABLE_TOOL_SEARCH=false loads the schemas of every deferred built-in Claude Code tool, not just Newton's: Opus MCP trials started at 30k tokens instead of 15k. h3 marks only the Newton server alwaysLoad, which gives 14.9k with no tool-search round trip. (2) Checkpoints and resets restored every scalar attribute of the hosted example, so a look-ahead or gain the agent set before rollout(start=True) was silently reverted, and one sweep returned identical rows. h3 rewinds only the scalars that step() itself advances. (3) An Opus grasp session crashed with CUDA error 700 after live solver experiments. Reproducing it showed that h1's recapture was unsafe. Newton examples capture a graph around the solver's first step, and SolverMuJoCo allocates buffers during that step, so those buffers belong to the first graph. Recording a second graph around the same solver either segfaults or silently corrupts the simulation (a grasped cube ended 99 m below the table). A one-box scene fails the same way, and one eager step before the first capture avoids it. h3 recaptures only when example.solver has been replaced, which is safe. For other changes it reports that values inside the captured graphs keep their old values until a rebuild. recapture() refuses to run around the same solver. The grasp and G1 MCP trials of iterations 1 and 2 hit such recaptures (for example 10 times in the i2 Opus grasp trial). Their live numbers may have been corrupted, although their verified submissions were not affected.

h3 → h4. With h3, the MCP's first turn was still 2.5k tokens larger than the no-MCP baseline's. Part of that came from the host guide appearing twice: once in the task prompt and again in the server instructions. h4 adds --no-app-guide to the stdio bridge, and the harness uses it because its prompts carry the guide. Hosting was also extended to kinematic examples without a dynamics solver or second state (such as the grinding scene), and the host guide now says that non-array objects such as SDFs are not rewound by reset.

h4 → h5. Iteration 4 exposed three gaps. (1) Hosted examples run with a null viewer, so geometry an example draws itself in render(), such as the ground workpiece surface, was invisible to observe, and an agent plotted it with matplotlib instead. The host's viewer now records log_mesh calls, and color observations composite those meshes over the model's shapes by depth; auto-framing uses mesh bounds. (2) The MuJoCo capture bug struck again through ordinary task code. Astra called the task's own rollout() on the example's already-captured solver, and the live process could no longer allocate memory. An eager step on scratch states followed by solver.reset() prevents this even in the minimal repro, so the host process now warms every SolverMuJoCo this way; physics is unchanged (the grasp scene matches to seven digits). (3) With the CUDA context broken, the agent had to restart the host by hand. newton_rebuild(arguments={"restart": true}) now re-executes the host process, and the MCP client re-reads the connection file and retries when its server restarts. The host guide also recommends workers.map over submit for sweeps, because polling a future had cost an extra turn per sweep.

4. Real-robot calibration data

The system-identification task uses public measurements from the DFKI underactuated double pendulum (BSD-3-Clause). The robot has two quasi-direct-drive AK80-6 motors with 6:1 gearing, a 0.2 m first link, and a 0.3 m second link. Its fourteen design C.0 system-identification runs record measured joint angles, velocities, and motor torques. Runs 00–09 are given to the agent, while runs 10 (20 s excitation) and 11 (75 s, full swings, 300 Hz) are held out. The model replicates one pendulum per evaluation window as a separate Newton world, so a whole recording is evaluated in one batched SolverMuJoCo rollout (about 0.5 s on the study GPU).

The thresholds were set before any agent trial, from three reference parameter sets. The nominal starter misses badly. The published DFKI identification, mapped to a physically valid Newton model, roughly halves the error but does not pass. A direct Nelder–Mead fit of all twelve Newton parameters to runs 07–09 passes with margin. So the gates reward calibrating the simulator itself, beyond copying published numbers.

The agents solved this task quickly and in the same way in both conditions. They fitted the identifiable base parameters by linear least squares on inverse dynamics, then refined them with their own NumPy (Opus) or C++ (Astra) forward models under the multiple-shooting objective, and used Newton only to confirm. On a two-link system the simulator is not needed in the inner loop, so the live MCP has little to offer here. Its value should show on systems where the simulator is the only practical forward model, with contact or many degrees of freedom.

From iteration 3 a second real dataset is used where the simulator is the practical forward model: the ContactNets cube tosses (BSD-3-Clause), 570 hand tosses of an acrylic cube onto a wooden table tracked at 148 Hz (Pfrommer et al., CoRL 2020). The cube's size, mass, and inertia are measured and fixed. The agent calibrates contact behavior (friction, stiffness, damping, torsional friction, table height, solver settings) so that open-loop rollouts from each toss's first frame reproduce the recorded bounces, slides, and tumbles. Each toss is one Newton world, and a CUDA-graph rollout of all 400 training tosses takes about 2–4 s.

The thresholds were set before any agent trial. Published parameters do not transfer. The ContactNets friction coefficient with untuned stiffness halves the position error but leaves orientation unchanged. The MuJoCo fit of Acosta et al., mapped to Newton's contact model, is worse than friction alone, because stiffness and damping mean different things across simulators and timesteps. A Nelder–Mead fit of five Newton contact parameters on 200 training tosses passes with margin.

5. Findings so far

Frontier agents now solve these setup, tuning, and capability tasks with or without the MCP. All 72 verified trials so far passed, including the SDF-grinding capability task. The harness therefore has to earn its place through efficiency and reliability, and the tasks are no longer hard enough to show differences in success.

Harness details decide whether the MCP saves or costs tokens. The same live session went from 1.19× input tokens (h1) to 0.74–0.81× (h3–h4) through changes in how tools are advertised and loaded, what the helpers return, and how resets behave. One setting pushed Opus to 1.63× before it was reverted. Per-turn fixed context and extra turns explain the overhead, not tool output.

The MCP saves wall-clock time most reliably when fresh runs are expensive or iteration is tight. Across all pairs it was faster in 24 of 36 (0.81×). The largest gains were on G1 tracking (up to 2.9× faster) and grasp drift. On the pendulum and the grinding task, where fresh processes are cheap and agents can reason from the code, the two conditions were close. Remaining token overhead for Opus appears on tasks where it keeps exploring optional margins after passing, which neither condition's prompt discourages.

A live session needs guards that a restart workflow gets for free. Three silent-divergence bugs surfaced only through agent use: settings reverted by reset, stale bytecode after a quick edit, and memory corruption from recapturing a CUDA graph around a warm solver. A live harness is only as trustworthy as its bookkeeping, and each fix has a regression test.

The MuJoCo capture issue is a Newton bug worth fixing at the source. Capturing a CUDA graph around a new SolverMuJoCo leaves buffers allocated inside that graph, and a second capture around the same solver crashes, on upstream Newton main as well (repro in Section 7). One eager step on scratch states followed by reset() avoids it. Doing that in SolverMuJoCo.__init__, or allocating the buffers eagerly, would fix it for everyone; the MCP host applies the warm-up in its own process.

Explaining effective solver parameters saves investigation. Where an agent used the contact report, it found the grasp's root cause (finger priority overriding the cube's material) in its first call. Agents without it read solver kernels to reconstruct the same fact.

6. Limits

This is an exploratory loop, not a registered study. The harness changes between iterations, three to seven pairs per agent and iteration cannot separate small effects from noise, and tasks are added as the loop goes. All pairs ran on one shared 4-CPU machine with a MIG GPU slice. Concurrent pairs control for load between conditions but not across iterations, and reference fits sometimes ran during trials.

Iteration 0 has no Astra trials. One iteration-1 Astra G1 pair was excluded because the operator accidentally terminated its live host while testing workers; it was rerun with the same harness. Live results in some iteration-1 and iteration-2 MCP trials may have been corrupted by the recapture bug described in Section 3; their verified submissions were not. Codex does not report API cost. Because every task so far is solvable in both conditions, these results say nothing yet about whether the MCP raises success on harder problems.
