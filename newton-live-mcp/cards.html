Debug Cards for Newton agents

This page documents the 36 Debug Cards used in the cheaper-model phase of the Newton live-MCP study: how they were distilled from the study's transcripts and checked, how agents received them, what each card says, and how useful each one was in the 78 trials that had them. Usefulness comes from reading the transcripts: every time an agent opened a card, or the MCP host attached one, the following actions were classified as decisive, helpful, unused or misleading, with the evidence quoted below each card.

1. How the cards were made and delivered

Mining. Six readers, one per task family (G1 control, grasping, identification, physical replays, scene building from photos, visual tasks), read all 245 transcripts of iterations 0–17 (Opus 5.5 and GPT-6 Astra, with and without the MCP). They extracted episodes where agents struggled, giving the trial, line and time, and drafted 110 candidate cards with about 90 workflow lessons. A distiller merged them into 35 cards of at most about 250 words each, in the Text2Sim shape: symptoms, likely causes, checks (short Newton calls), repairs (directions, not values), and pitfalls. Workflow lessons went into the procedure instead.

Verification. A separate verifier checked every claim against the Newton tree the trials ran on:

  • It resolved all 62 API names the cards use.
  • It reproduced 14 warning and error scenarios in fresh CPU processes and tested every attachment signature against them and against the transcripts.
  • It corrected wrong claims in 23 cards. For example, a mass-dependence claim in CON-02 was disproved by a CPU test, the overflow messages in CON-06 were current only for older builds, and BAT-04 had the wrong call form.

Neutrality. Cards hold general Newton knowledge only: no task values and no verifier details. A search of the neutral copies for task names, trial ids and study terms found nothing; trial references appear only in this page's provenance notes, which agents never saw. One card, FIT-05, and a revision of CON-02 were added after v6.1 from its traces. Five of the six evaluation tasks were among the mined families; SDF grinding was not, and serves as the held-out task.

Delivery. The cards reached agents in three ways:

  • As an agent skill in the trial workspace (.claude/skills/ for Claude Code, .agents/skills/ for Codex), with an index.
  • From cards-v2 on, as a list of all titles in the prompt.
  • In MCP trials, through cards(query) and card(id) in live cells. The host also names a card in a reply, once per session, when the reply contains a message matching one of its signatures (20 cards have signatures, mostly exact Newton, MuJoCo Warp and Warp warning strings).
Arms without the harness never see the cards: the harness directory is masked in their sandbox.

Debug Cards: /WORKSPACE/.agents/skills/newton-debug-cards/INDEX.md lists notes on Newton simulation problems (symptom, likely causes, checks, repairs), one file per card in /WORKSPACE/.agents/skills/newton-debug-cards/cards/. In the live session, cards('query') and card('id') read the same cards (see the hosted script's notes above).

Procedure (for any Newton simulation task):
1. Criteria. Copy every stated requirement into CHECKLIST.md: each metric with its threshold and window, every stated variation (unseen cases, perturbations, rates), every limit and constraint, and the command verification runs.
2. Check script. Write check.py. It runs the deliverable the way verification will (a fresh process with the stated command), covers the closest local analog of each stated variation, and prints one line per criterion (value, threshold, worst-case margin) plus the minutes left. Run it on the starting files: this is your baseline.
3. Diagnose before tuning. Name the symptom and find its card in the Debug Card index (for an error or warning message, card MSG-01). Run the card's checks before reading Newton source. Before using an unfamiliar API, check its signature (inspect.signature, help) instead of guessing.
4. Experiment. Change one cause at a time. The first time you use a way of editing the model, apply an extreme value and confirm that the output changes. Time one evaluation, then run variants side by side where you can (newton.utils.BatchRollout). Log one line per experiment in NOTES.md: the change and the worst margin.
5. Loop monitor. After three experiments in a row that do not improve the worst margin, stop sweeping: split the error into its parts, look for a shared cause, and re-read the matching card.
6. Save. When check.py passes every criterion, copy the deliverable files to pass_<n>/ before changing anything else.
7. Finish. When every criterion passes with a clear margin (about 20%) in a fresh-process run of the stated command, report and stop. If a margin is thin and more than a quarter of the time is left, work only on that criterion, re-run check.py after each change, and restore the saved copy if anything regresses.
Shell: run anything longer than a minute in the background with output to a file and its own timeout, and poll with short commands; stop processes by their PID, never by pattern; name scratch files dbg_*.py.

Procedure (for any Newton simulation task):
1. Criteria. Copy every stated requirement into CHECKLIST.md: each metric with its threshold and window, every stated variation (unseen cases, perturbations, rates), every limit and constraint, and the command verification runs.
2. Measurement. Put the metric code in one module (metrics.py) that both your experiments and check.py import. Test it once on a case with a known answer (for example the reference compared with itself gives zero error) before trusting it.
3. Check script. check.py runs the deliverable the way verification will (a fresh process with the stated command), covers the closest local analog of each stated variation (if verification uses cases you cannot see, tune on part of your data and let check.py score the rest; cards FIT-05 and CTL-09), and prints one line per criterion (value, threshold, margin) plus the minutes left. 4. Diagnose before tuning. Name the symptom, find its card (for an error or warning message, card MSG-01), and run the card's checks before reading Newton source. Before using an unfamiliar API, check its signature (inspect.signature, help) instead of guessing.
5. Experiment quickly. Run experiments in-process (the live session if you have one, or one script that evaluates many variants, e.g. newton.utils.BatchRollout), not one fresh process per variant. Sweep the parameters you are allowed to change over a wide range (about 0.1x to 10x) before building new mechanisms. 8. Finish. When check.py passes every criterion with a clear margin (about 20%), report and stop; do not make cosmetic edits afterwards. If a margin is thin and more than a quarter of the time is left, work only on that criterion and restore the saved copy if anything regresses. BAT-01: A sweep returns the same result for very different settings: the edit never reached the solver

Edits and batches · introduced in cards-v1 · verification confidence: high · 1 attachment signature(s)

In short. A sweep that changes nothing usually means the edit never reached the solver: wrong ModelFlags, a construction-only field, only world 0, or a dropped value. Test the edit path with an extreme value first.

Mined from. 7 grasp_drift trials misattributed nulls (one positive control settled it in ~10 s); 6 replay + 2 abc_arm no-op edits; unapplied perturbations in 3 abc_scratch MCP trials (~1200 s each in two, one failure).

Verification. Never-read list completed (joint_enabled, body_inv_mass/inv_inertia, kf only with Newton contacts).

Full card text (as given to agents in cards-v3)

Symptoms

  • A sweep is flat, or a 'robustness' batch shows no spread.

Likely causes

  • Missing or wrong ModelFlags: gravcomp and mass/inertia need BODY_INERTIAL_PROPERTIES (not BODY_PROPERTIES); armature JOINT_DOF_INERTIAL_PROPERTIES; gains, damping, friction, limits JOINT_DOF_FORCE_PROPERTIES; shape materials, gap, solimp SHAPE_PROPERTIES; equality solref CONSTRAINT_PROPERTIES.
  • Construction-only: geom priority, condim, ctrl_source, joint_target_mode, solver options (cone, iterations, integrator, impratio). Never read by SolverMuJoCo: restitution, joint_velocity_limit, joint_enabled, body_inv_mass/inv_inertia; kf only with Newton contacts.
  • Inactive mode (mujoco.solref outside RAW mode) or the wrong array (CTL-01).
  • Only world 0 edited (BAT-02); a captured graph replays old pointers (BAT-04); reset/restore re-applied old values; the scenario setup never applied its perturbation.
  • Your harness dropped the value (JSON int keys became str, a stale variable). Or the knob is real but irrelevant (CON-03).

Checks

  • Positive control: push an extreme value through the same path; the output must change grossly.
  • report_solver_params(solver, kind) pending column (MCP solver_params); solver.check_world_values(name).
  • Read back the t=0 state of every world after scenario setup.

Repairs

  • Use the right flag, or rebuild the solver for construction-time fields and re-capture graphs; set values at build time in the script.

BLD-03: Calibrated camera: projected points miss the photo, or pixel-to-world placement is off

Full card text (as given to agents in cards-v3)

Symptoms

Likely causes

Mined from. Mapping re-derived from kernels.py in 16/22 cube_toss trials and ~892 s over grasp_drift restart trials; mass normalization diagnosed in 5 replay trials (150-300 s); >=21/24 replay finals stiffened contacts.

Full card text (as given to agents in cards-v3)

Symptoms

Likely causes

  • The mapping depends on model.mujoco.solref_mode and the contact path. Builder shapes default to legacy MJCF_DEFAULT: unit-mass numerics timeconst = 2/kd, dampratio = kd/(2*sqrt(ke)), not N/m. Contacts and friction · introduced in cards-v1 · verification confidence: medium · 1 attachment signature(s)

In short. Slow creep of a firmly held object is the discretization floor of soft friction, which scales with dt; no contact parameter removes it. Report it and stop.

Mined from. 18/18 Opus grasp_drift trials hunted it after passing (median ~440 s, ~8.4 ks total, one gain); noslip searched in 23/32; rk4 worse 6/6; creep halved with dt (i4/grasp_drift-opus-restart-p0 L392-L421).

Symptoms

  • A stiff grasp still slides along the pads at a constant slow rate; no rotation, fingers fixed to the hand.

  • Discretization floor of soft friction: friction rows act on velocity with a reference time constant clamped to 2*dt (refsafe), so slip scales with dt; it is not Coulomb slip.

FIT-05: A calibration passes on the data you have but fails on unseen recordings

Fitting to data · introduced in cards-v2 · verification confidence: added · no attachment signature

In short. A calibration that passes on the provided data but fails unseen cases: tune on part of the data, check on the rest, and stop tuning below the noise floor (added in cards-v2).

Mined from. Added in cards-v2 from the v6.1 traces (cube toss and ABC arm calibrations that passed on the provided data and failed unseen cases).

Full card text (as given to agents in cards-v3)

Symptoms

  • A fit that passes on all provided data fails on held-out cases by a small amount.
  • Score differences between candidates are smaller than the spread between recordings.

Likely causes

  • Tuning on every provided case leaves no estimate of the error on new cases: the margin you see is optimistic.
  • Fine grids (many digits) fit the noise of the sample, not the physics.
  • Extra mechanisms (another solver, extra friction terms, offsets) add freedom that lowers the training error without improving prediction.

Checks

  • Split the provided cases (for example even and odd indices, or by recording): tune on one half and score the other. The gap between the two is your noise floor.
  • Per-case error distribution: a few bad cases can dominate the mean; check which cases carry the error and whether held-out-like cases resemble them.
  • Refit on the other split: parameters that move by more than their sweep step are not identified (FIT-01).

Repairs

  • Accept a candidate only on the held-out half, with a margin larger than the train/held-out gap; report both scores.
  • Prefer a few physically meaningful parameters (damping ratio, friction, support height, delay) estimated from data over many tuned ones; stop refining below the noise floor.
  • After choosing, refit on all data only if the held-out score stays within the margin.

Pitfalls / shortcuts to avoid

  • Grids finer than the noise floor; switching solvers or adding mechanisms to recover the last few percent on training data; reporting the training score as the expected verification score.
