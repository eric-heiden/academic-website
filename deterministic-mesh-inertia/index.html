Harness Note

The V2 rerun uses the latest PR #1355 checkout and compiles the original atomic kernels directly with deterministic module options. Warp captures the global deterministic setting when the kernel module is created, so setting wp.config.deterministic later, after @wp.kernel decoration, is not enough for an existing module. 

@wp.kernel(module="unique", module_options={"deterministic": wp.DeterministicMode.RUN_TO_RUN}, enable_backward=False)
def atomic_solid_mesh_inertia(...):
    ...
    wp.atomic_add(volume, 0, v)
    wp.atomic_add(first, 0, f)
    wp.atomic_add(second, 0, s)

Why V2 Is Slow

PR #1355 makes the all-to-one atomics bit-exact by recording scatter updates, sorting them, and reducing them after the kernel. The original mesh inertia path emits three forward scatter targets per triangle: volume has 1 float component, first has 3, and second has 9. The mat33 target dominates the cost.

150k-record deterministic post-pass targetComponentsMeasured time
volume / scalar float10.28 ms after warmup
first / vec3382.0 ms
second / mat339363.8 ms

The scalar RUN_TO_RUN path has a specialized reduce-by-key implementation. Multi-component values currently use Warp's generic deterministic path: after sorting, one segment-head thread walks the whole destination segment sequentially for each component. For this workload every record targets index 0, so the mat33 pass is effectively one thread doing 150k ordered additions for each of 9 components.

Runtime

V2 pays for deterministic atomic ordering. It is bit-exact, but it is not competitive with V3 for this Newton importer workload. V3 avoids scalar atomic reduction order entirely and is faster than V0 on this run.
