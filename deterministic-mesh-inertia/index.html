TL;DR

Current status: Newton main no longer uses wp.atomic_add for mesh-inertia reductions. As of 40fed42d, the implementation uses the V3 design from this report: a single tiled launch with wp.tile_sum over fixed lanes. A fresh 2026-06-12 verification with latest Warp PR #1355 produced bit-exact solid and hollow mesh inertia results: 1 unique hash across 30 reruns for each of NOT_GUARANTEED, RUN_TO_RUN, and GPU_TO_GPU on a 46,786-triangle synthetic mesh.

The historical June 10 benchmark below explains why that change was needed. The old atomic baseline drifted on 262 / 262 meshes, V3 recovered bit-exact determinism with only ~2 % runtime overhead, and V2 (Warp PR #1355 automatic RUN_TO_RUN lowering) drifted on 10 / 262 dense meshes in that historical run. The June 11 scalar repro isolated that drift to PR #1355's scalar CUB DeviceReduce::ReduceByKey path, not to Newton postprocessing. The latest PR #1355 head now fixes the pure scalar Warp repro after a clean rebuild.

2 · Runtime

V3 (tile_sum) is within noise of V0 on every robot. V1 pays for writing per-triangle device buffers and reducing them on the host. V2 pays for deterministic scatter buffers, a record-count readback outside graph capture, and CUB sort/reduce postpasses. That fixed machinery dominates this single-output reduction workload; for very large meshes (apptronik_apollo, G1) the relative overhead drops.

3 · Determinism on the baseline

V0 (the old atomic baseline) is non-deterministic on 262/262 meshes across 5 reruns. Drift summary (relative ‖I‖ across reruns):

  • Median: 8.51e-06
  • p99: 2.36e-04
  • Worst case: 2.80e-03 — robot apptronik_apollo, 45,358 triangles

The 5 worst-case rerun masses for that mesh are: 1.755395e-04, 1.755405e-04, 1.755405e-04, 1.755408e-04, 1.755403e-04. Five separate runs, five different numerical answers from the same input — this is exactly the kind of nondeterminism that breaks hash-based snapshot regression tests on Newton models.

The log-binned chart below shows the absolute drift distribution. The bimodal shape is real: very small meshes drift in the 1e-15 to 1e-10 range (sub-ULP for f32 / numerical noise); large meshes drift in the 1 to 1e5 range (because both the per-triangle integrand and the absolute inertia magnitude grow with mesh size).

4 · Accuracy vs V1 (f64 host-reduce reference)

V0's relative inertia error (vs V1's deterministic f64 result) tracks the run-to-run drift — V0 isn't wrong, it's variable, and V1's f64 fold is just a deterministic realization of the same expectation with one extra digit of precision. V3 (tile_sum in float32) is consistently ~1 order of magnitude more accurate than V0 or V2 against V1 across all robots, suggesting Warp's tile_sum tree reduction is numerically better-conditioned than either GPU atomics or CUB scatter-sort-reduce in f32.

5 · Does f64 accumulation matter?

This was the central question. We compare:

  • V1 — kernel still f32 per-triangle, but the final accumulation is explicitly promoted to numpy.float64 and summed.
  • V3 — entirely in f32, but reduced inside the kernel via wp.tile_sum (tree reduction).
  • V0 — entirely in f32, GPU atomic add (non-deterministic, but the same precision class as V2/V3 on average).

Worst-case relative inertia error V3 (f32 tile_sum) vs V1 (f64 host-reduce) across all 262 meshes is 3.57e-05, with p99 of 8.43e-06. For comparison, V0's run-to-run drift alone is ~5e-04 worst-case.

Bottom line: the precision gap between f64 host-reduce and f32 in-kernel tile_sum is on the same order as V0's run-to-run drift. Both are well below Newton's existing 1e-5 relative symmetry tolerance and far below the integration-noise floor of physics steps. For certification-grade reproducibility the deciding factor is determinism, not f64 precision per se — and V3 delivers determinism at no measurable runtime cost.

6 · Warp PR #1355 deep dive (V2)

The motivation for V2 was: can we get determinism with no source changes, just by setting wp.config.deterministic = run_to_run? The answer on this workload is almost yes, but the scalar reduction fast path is still a problem:

  • Determinism: 10 of 262 meshes still drift across 5 reruns. All drifting meshes are large (≥36 k triangles), all on G1 / H1 / Apollo, and the raw saved rows show the first differing field is volume / mass, with deltas between 7.28e-12 and 9.31e-10. The old implementation used in this V2 benchmark computed volume with the simple pattern wp.atomic_add(volume, 0, value). PR #1355 sorts scalar records by packed destination/thread key, then reduces them by destination through CUB DeviceReduce::ReduceByKey in RUN_TO_RUN mode. A local standalone scalar probe reproduced multiple hashes for that exact pattern. Disabling only that scalar shortcut made RUN_TO_RUN bit-exact and equal to GPU_TO_GPU, while an independent scatter + radix-sort probe produced byte-identical sorted keys and values across reruns. This isolates the remaining drift to the scalar CUB ReduceByKey reducer path.
  • Performance: median +551 % vs V0 (19 ms vs 2.9 ms per call). The CUB scatter-sort-reduce path has fixed overhead per launch that dominates these very small (single output slot) reductions. p90 is +2118 % (94 ms vs 4.2 ms) because the largest meshes pay a worst-case sort cost.
  • Accuracy: max relative ‖I‖ error vs V1 of 2.91e-04, same order as V0 (which makes sense: both do f32 reduction, V2 just in a deterministic order).

Local follow-up on 2026-06-11 used a fresh checkout of git@github.com:NVIDIA/warp.git, fetched PR #1355 as a git remote ref, built it locally in /home/horde/repos/warp-pr1355-local/.venv, and installed the then-current Newton main into that same venv. A synthetic scalar atomic_add(out, 0, value) probe under RUN_TO_RUN produced 3 unique hashes at 42,802 terms, 3 at 46,786 terms, and 2 at 70,000 terms across 50 reruns. The same scalar probe under GPU_TO_GPU produced 1 hash for every tested size, and a vec3 RUN_TO_RUN probe also produced 1 hash for every tested size. A synthetic Newton compute_inertia_mesh case with 46,786 triangles produced 4 hashes over 30 reruns under RUN_TO_RUN and 1 hash over 30 reruns under GPU_TO_GPU. After temporarily routing scalar RUN_TO_RUN through Warp's generic sequential segmented reducer, the same scalar sizes produced 1 hash across 50 reruns and matched GPU_TO_GPU exactly.

Latest follow-up on 2026-06-12 fetched PR #1355 again and fast-forwarded it from e78684d21 to 825f50ce6. The rebuild was done from a clean native object set in /home/horde/repos/warp-pr1355-local/.venv-pr1355-verify. The pure Warp scalar repro now passes: atomic_add(out, 0, value) under RUN_TO_RUN produced 1 unique output across 100 reruns (18.162202835083008, 0x41914c31), and GPU_TO_GPU also produced 1 unique output. Newton main had advanced to 40fed42d and now includes 811968bf ("Deterministic inertia tensor computation"). Current Newton mesh inertia no longer exercises the scalar atomic lowering path: on a 46,786-triangle synthetic mesh, both solid and hollow compute_inertia_mesh produced 1 unique hash across 30 reruns under NOT_GUARANTEED, RUN_TO_RUN, and GPU_TO_GPU. Newton's targeted test_mesh_inertia_is_deterministic also passed under the rebuilt PR #1355 venv.

For comparison, a stripped-down hand-rolled equivalent (each thread writes to its own buffer slot, then host-side numpy.sum in f32) gives bit-exact determinism (0/262 drift) at only +30 % runtime. This is structurally similar to V1 except it stays in f32. The current PR #1355 head appears to fix the scalar RUN_TO_RUN piece that caused the historical V2 drift, but the full 262-mesh V2 timing matrix above has not been regenerated with 825f50ce6. Current Newton main already uses the lower-overhead V3 tile-sum implementation.

7 · Memory footprint

V0 / V3 keep a constant ~52 byte accumulator per launch; V1 / V2 allocate num_tris × 52 byte output buffers. For the largest mesh in the test set (G1's torso at 51 k triangles → 2.6 MiB; apollo's biggest at 122 k → 6.3 MiB), V1/V2 still fit comfortably in the L40's mempool. On 100 k+ tri meshes, V1's allocator chatter is the dominant cost — exactly what the V3 tile_sum rewrite avoids.
