Newton selection and USD import design

Newton assets without ArticulationRootAPI

Investigation of how Newton should treat USD mechanisms that author rigid bodies and joints but no articulation root. The focus is RL-facing selection APIs, cyclic mechanisms, and whether importer-side compatibility should synthesize articulations.

Executive summary

Fix the importer inconsistency

The local Newton fix is the right baseline: rootless body-to-world fixed joints should remain orphan joints, not create a one-joint articulation while the rest of the mechanism stays in articulation -1.

Add a joint-centric selection API

A JointView in newton.selection should be the primary RL answer for no-root maximal-coordinate mechanisms. It can query and set joint state, targets, and controls by path without pretending there is a kinematic tree.

Keep invented articulations opt-in

Importer-inferred articulations are useful for compatibility with ArticulationView, FK, and MuJoCo, but cyclic models require deterministic tree/loop partitioning and joint reordering. This should not be silent default behavior.

Recommendation: implement JointView first, then add an explicit importer compatibility mode such as rootless_articulation_policy="infer_tree". Do not ask Isaac Lab to own this as a permanent ClosedLoopView workaround; the abstraction belongs in Newton because Newton owns the canonical joint labels, coordinate ranges, solver compatibility, and articulation metadata.

For Isaac Lab, the required replacement is larger than returning a list of joints. Isaac Lab's ArticulationData is a cached, batched tensor interface for robot state, default reset state, body/link state, joint state, joint properties, limits, and command targets. JointView is the right low-level primitive for rootless mechanisms, but Isaac Lab also needs a mechanism-level composition of joint, body, and root views to preserve its reset, observation, reward, and actuator paths.

What changed in Newton

The bug was not that Newton refused to treat a rootless asset as an articulation. The bug was that one special case did synthesize an articulation: a body-to-world fixed joint with no PhysicsArticulationRootAPI. That produced mixed metadata: the root joint belonged to articulation 0 while the rest of the asset remained in articulation -1.

The committed fix removes that special case. A no-root asset now imports consistently as a set of orphan joints. Normal finalize() raises and tells the caller to use skip_validation_joints=True; maximal-coordinate solvers can then consume the authored joint graph directly.

This is deliberately not a user experience endpoint. It is a better invariant: no USD articulation root means no Newton articulation metadata unless a caller explicitly requests compatibility inference.

Option 1: add JointView

ArticulationView starts from model.articulation_label. If model.articulation_count == 0, it raises KeyError before joint filters can help. That is correct for an articulation view, but it leaves RL users without a public, vectorized way to address joint state and control slots for rootless mechanisms.

A JointView should select directly from model.joint_label, then derive coordinate and DOF ranges from joint_q_start and joint_qd_start. It should provide the joint-state subset of ArticulationView, not the tree-only operations.

Recommended surface

  • JointView(model, pattern, include_joints=None, exclude_joints=None, include_joint_types=None, exclude_joint_types=None)
  • Expose joint_ids, joint_labels, joint_coord_ids, and joint_dof_ids.
  • Implement get_joint_positions(), set_joint_positions(), get_joint_velocities(), set_joint_velocities(), target getters/setters, and control-force setters.
  • Expose joint properties needed by controllers and RL wrappers: stiffness, damping, armature, friction, position limits, velocity limits, effort limits, soft limits, and gear ratios when present.
  • Validate shape uniformity across worlds for batched RL use, mirroring the useful parts of ArticulationView.
  • Use Warp gather/scatter kernels, not repeated Python .numpy() indexing, for production paths.

Isaac Lab contract

Isaac Lab's ArticulationData assumes that every robot asset has a batched view with stable names and tensor shapes. It lazily caches root state, body/link state, joint positions, joint velocities, joint accelerations, default reset values, and simulation-facing joint properties. That means a Newton-facing replacement must support the following paths, not only observation reads:

  • Stable joint_names, body_names, and deterministic per-environment ordering.
  • Batched joint state tensors shaped like (num_envs, num_joints) for positions, velocities, and accelerations.
  • Batched writes for resets and control, including joint state, position/velocity targets, actuator effort, and direct joint forces.
  • Joint metadata for actuator setup, clipping, domain randomization, and reward terms: limits, stiffness, damping, friction, armature, effort limits, velocity limits, and gear ratios.
  • Body/link transforms and velocities for observations, rewards, termination checks, frame transforms, and contact/sensor plumbing.
  • A root/base convention for no-root mechanisms, especially the distinction between fixed-base, authored floating-base, and implicit floating-base assets.

This is the best near-term architectural move. It supports no-root mechanisms, explicit USD articulations, and loop-closing joints without changing importer semantics. It also gives Isaac Lab a Newton-native replacement for PR #6027's closed-loop workaround.

Limit the promise: JointView should not imply FK, mass matrix, root-body state, or tree semantics. For Isaac Lab compatibility, compose it with a BodyView or higher-level MechanismView; do not overload a joint-only selector with root and body semantics.

Option 2: infer articulations in the importer

The importer can also synthesize a compatibility articulation for a connected joint component with no USD articulation root. The safe version is not to put every joint in an articulation. For cyclic mechanisms, the importer must choose a spanning tree and leave loop-closing joints outside the tree.

Newton already has the metadata shape for this: articulation_start points at the first tree joint, articulation_end points after the regular tree joints, and the next articulation_start acts as the upper bound when include_loop_closing_joints=True. The ordered synthetic four-bar and boxes_fourbar.usda both confirm that ArticulationView then skips loop joints by default and includes them when requested.

Importer requirements

  • Partition each rootless connected component into a deterministic spanning tree and loop-closing edge set.
  • Emit or reorder joints so the tree block is contiguous and any loop joints for that component immediately follow it.
  • Add the articulation only for the tree block. Leave loop joints with joint_articulation == -1 so validation treats them as loop joints, not true orphans.
  • Report the inferred root, tree joints, and loop joints in verbose output or a structured import summary.
  • Keep this behind an explicit option, for example rootless_articulation_policy="infer_tree".

Do not silently invent articulations by default. It changes joint order, coordinate order, and view behavior; it also makes one arbitrary tree choice in a mechanism whose USD author may have intentionally avoided articulation semantics.

For Kamino, the key implication is that loop joints must remain solver-visible as joints. The no-root solver smoke below shows Kamino can step the pure orphan-joint version. An inferred-articulation mode should be tested to ensure Kamino still consumes the loop tail, while ArticulationView defaults remain tree-only unless include_loop_closing_joints=True.

Isaac Lab context

Isaac Lab PR #6027 adds a ClosedLoopView to work around the same limitation: cyclic or rootless assets need joint state and control access, but ArticulationView is articulated-tree-centric. The prototype duck-types enough of Newton's ArticulationView for ArticulationData to read model, state, and control arrays directly.

The need is broader than closed-loop observation. Isaac Lab's ArticulationData is the object behind Articulation.data; tasks, managers, actuators, and reset logic use it as the canonical batched robot interface. It stores names, default root and joint state, default mass and inertia, joint limits and actuator properties, and lazily computed root, body, COM, and joint-state tensors. In practical RL terms, it feeds observations and rewards, scopes resets by environment, clips actions, applies actuator models, and restores default state.

This means JointView should provide the joint slice of that contract, while a Newton MechanismView or JointView + BodyView composition should provide the full asset contract. Otherwise Isaac Lab still has to infer root/body layout, per-world strides, implicit free-base behavior, and coordinate offsets from raw Newton arrays.

Minimum Newton primitive

JointView should own label matching, joint-to-coordinate mapping, joint state reads/writes, command writes, and joint property tensors. This removes the most fragile part of the current workaround.

Isaac Lab adapter

A higher-level adapter should combine JointView with body and root access so ArticulationData-like code can keep its existing batched reset, observation, reward, and actuator assumptions.

Compatibility inference

Importer-inferred articulations remain useful when users need tree-only APIs, but they should be an explicit compatibility mode rather than the default path for maximal-coordinate mechanisms.

The right home is Newton. Isaac Lab should not need to guess Newton's joint-coordinate layout or duplicate selection semantics. Newton can expose the global joint and body slices that maximal-coordinate solvers already use, while preserving an opt-in inferred-articulation path for FK, MuJoCo, and tree-compatible tooling.

Recommended implementation plan

  1. Add newton.selection.JointView with path matching over joint labels and batched gather/scatter for joint state, targets, and controls.
  2. Add or compose body/root access as BodyView or MechanismView so Isaac Lab can replace ClosedLoopView without rebuilding Newton array-stride logic in Isaac Lab.
  3. Expose the Isaac Lab-critical metadata: stable joint/body names, per-world ordering, joint coordinate and DOF ids, joint limits, effort/velocity limits, stiffness, damping, friction, armature, and default state helpers.
  4. Update the importer warning to point rootless-joint users at JointView or MechanismView for maximal-coordinate workflows and at the future inference option for tree-compatibility workflows.
  5. Add importer option rootless_articulation_policy="none" | "infer_tree". Keep "none" as default.
  6. When inference is enabled, build a deterministic spanning forest, emit tree joints first, emit loop joints immediately after each tree, and store an import summary of inferred tree and loop joints.
  7. Add regression coverage for the four cases in this report: open no-root chain, ordered four-bar, boxes_fourbar.usda, and both fourbar pole no-root variants.

Short version: do not force rootless mechanisms into ArticulationView just to make RL possible. Give RL a joint-native view, and make articulation inference an explicit compatibility layer for tree-only consumers.
