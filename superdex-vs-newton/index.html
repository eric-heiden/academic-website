01 · Orientation

Start with the task, not the solver label.

The projects overlap, but their user journeys are different. Newton presents a broad simulation toolkit with explicit data flow and a menu of solvers. SuperDex presents a live scene, packaged robot assets, and one integrated physics system. A useful comparison asks how much work remains between installation and a representative robot outcome.

How to read the evidence

Three levels of support

Ready example means a task, robot, controller, contacts, and visible outcome run together at the pinned revision. Building block means relevant assets or APIs ship, but the end-to-end task does not. Gap means the attempted path needs re-authoring or additional implementation.

Newton in one sentence

Explicit, array-oriented, and broad

Users choose how models, state, contacts, controls, solvers, worlds, and viewers fit together. The setup is longer, but the same concepts extend to GPU batches and mixed workloads.

SuperDex in one sentence

Scene-oriented and compact

Users create actors or packaged bots inside a mutable scene and advance it with one step call. Studio and native prefabs provide a cohesive authoring path for a single detailed scene.

A reader’s route

Move from promise to task to evidence.

The most useful comparison follows the path a new user would take. It begins with what each project makes easy to discover, continues through a representative robot task, and only then uses architecture to explain the outcome.

  1. 01
    Set the boundary

    Pin the revisions and distinguish complete examples, reusable building blocks, and project demonstrations.

  2. 02
    Follow the user journey

    Ask whether the robot, control, contacts, and a checkable outcome arrive as one usable path.

  3. 03

    Treat missing task scaffolding as integration work at this snapshot—not as a limit on what the engine could support.

The short answer

For the three workloads in this report, Newton currently provides the more complete path from repository to runnable robot task. SuperDex is especially attractive when a user begins with its native bot assets, Studio workflow, integrated contact model, and scene-level API—but matching these exact tasks still requires more task authoring.

Comparison boundary. The task traces and ViewerGL footage below are direct runs of Newton at the pinned revision. SuperDex gallery clips are first-party demonstrations of its broader manipulation and cloth capabilities; they are shown as capability context, not as matched benchmark results. No throughput ranking is inferred from unlike scenes.

Important context

SuperDex’s manipulation story is broader than the matched task.

The first-party gallery shows high-contact dexterous scenes that go beyond a two-finger grasp. That is a real strength. The distinction here is between a demonstrated project capability and a downloadable example that a user can run, modify, and test immediately.

The fairest next comparison would use one shared robot/object asset and one shared success condition, while letting each engine use its native contact and control stack.

06 · Background

Two coherent simulation shapes.

The differences above follow directly from the public architecture. Newton separates model data, collision, state, control, and solver choice. SuperDex assembles rigid, articulated, soft, shell, and rod actors inside one scene and advances that scene through an implicit solve.

Newton

A simulator toolkit with interchangeable physics paths

  • Eight first-party solver families cover articulated bodies, deformables, cloth, MPM, and hard-contact experiments.
  • Topology is finalized; state, control, contacts, and many model arrays remain directly accessible.
  • World replication and device arrays make many environments a core modeling primitive.
  • URDF, MJCF, and USD can enter through public Python APIs.
  • ViewerGL, RTX, Rerun, Viser, USD, file playback, and null execution share one viewer interface.
Project SuperDex

A live scene with integrated implicit physics

  • Rigid, articulated, FEM soft, shell, and rod actors contribute to one scene-level solve.
  • Actors, bots, controllers, sensors, and scene snapshots use object-oriented handles.
  • Native bot and task prefabs pair with a dedicated Studio authoring and validation workflow.
  • Rods, tendons, soft actors, and shell contact are visible first-class concepts.
  • Current public wheels execute physics on CPU; Lab scales environments with local and worker processes.
Main-branch context. The SuperDex snapshot includes development after its 1.0 tag: direct per-pair contact overrides, prefab additions, package-path cleanup, linear-solver changes, and shell-storage work. Newton’s snapshot includes the 1.6 development API, MuJoCo Warp 3.12, the explicit collision pipeline, new controller surfaces, and recent hydroelastic-contact work.
07 · API ergonomics

Which API feels easier from the user’s seat?

SuperDex is usually shorter for one already-authored scene. Newton asks for more decisions at setup time, but those objects become useful when users need a different solver, direct arrays, explicit contacts, or hundreds of worlds.

SuperDex ergonomic advantage

One scene, compact lifecycle

The ordinary mental model is direct: initialize, create a scene, add actors or bots, and call scene.step(dt). Whole-scene capture and restore is similarly cohesive.

Newton ergonomic advantage

Explicit data that scales with the experiment

Model, solver, collision, state, and control are separate on purpose. The API is more verbose, while making device placement, batching, solver swaps, and custom loops legible.

Newton · shape of a single-robot loop
builder = newton.ModelBuilder()
builder.add_urdf("robot.urdf", floating=False)
builder.add_ground_plane()
model = builder.finalize()

solver = newton.solvers.SolverXPBD(model)
state_a, state_b = model.state(), model.state()
control = model.control()
pipeline = newton.CollisionPipeline(model)
contacts = pipeline.contacts()

newton.eval_fk(model, model.joint_q, model.joint_qd, state_a)

for _ in range(200):
    state_a.clear_forces()
    pipeline.collide(state_a, contacts)
    solver.step(state_a, state_b, control, contacts, 1 / 200)
    state_a, state_b = state_b, state_a
SuperDex · shape of a single-robot loop
sdp.initialize(num_worker_threads=0)
try:
    scene = sdp.create_scene("robot")
    scene.set_gravity([0, 0, -9.81])

    prefab = sdr.load_bot_prefab_from_file("robot.superdex_bot")
    context = sdr.create_context()
    bot = sdr.create_bot(scene, prefab, context)

    for _ in range(200):
        scene.step(1 / 200)

    sdr.destroy_bot(scene, bot)
finally:
    sdp.shutdown()
Ergonomic conclusion. SuperDex is more concise for a native, single-scene application and provides a particularly nice whole-scene snapshot concept. Newton is easier to extend when the experiment itself revolves around solver selection, GPU arrays, batched worlds, or multiple visualization backends. Neither is simply “better”; the shorter API serves a narrower default path.
08 · Gap map

Where each project is more complete.

These are observable gaps at the pinned commits, not a proposed roadmap. They identify where a user can proceed with existing artifacts and where custom integration begins.

More complete in Newton

Robot tasks and experiment scale

  • Shipped G1 policy locomotion
  • Checked parallel-gripper pick-and-place
  • Robot–cloth examples on H1 and Franka
  • Native many-world model replication
  • Broader direct import and viewer choices
More complete in SuperDex

Native scene and authoring cohesion

  • Compact mutable-scene lifecycle
  • Studio-backed bot and prefab authoring
  • First-class rod, tendon, and muscle concepts
  • Whole-scene capture and restore
  • Direct Gymnasium environment surface
Open comparison work

Evidence both ecosystems would benefit from

  • Shared robot and object assets
  • Common task-success definitions
  • Matched contact and control assumptions
  • Repeatable robot-task performance suites
  • Versioned expected outcomes for examples
Decision guide

Choose Newton when today’s work centers on GPU world replication, existing humanoid or manipulation examples, solver choice, or direct simulation arrays. Choose SuperDex when the application fits its native asset pipeline and values a compact scene API, Studio workflow, monolithic multi-material contact, and Gymnasium-facing environment layer. Prototype the exact contact task before committing either way.
