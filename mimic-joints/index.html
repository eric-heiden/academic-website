Should Mimics Be Joints?

Updated report on treating URDF/USD mimic relationships as zero-DOF Newton joints. This version focuses on Model parameterization, reuse of existing joint attributes, benchmark numbers, and the design trade-off between a joint-topology representation and separate mimic constraints.

Executive summary

Best semantic model

Mimic followers are kinematic joints in the body tree: they have parent/child bodies, fixed parent/child frames, labels, world membership, and enabled state. Reusing those existing joint attributes is a real win.

Best storage model

Do not add dense mimic-only arrays on every joint if this becomes production API. Use a compact, generic affine joint-relation table keyed by joint index, or keep the existing constraint table.

Practical verdict

Keep mimics as joints for FK/import/export, but lower to solver-specific constraints where needed. If Newton will not add a generic relation table, keeping mimics as a separate concept is cleaner than adding permanent mimic-only Model arrays.

Numerically, joint-based import reduces Robotiq generalized coordinates from 6 to 1 in the synthetic URDF and 14/12 to 6/6 in imported Robotiq models, improving FK by 30–40% on those assets. Solver timing is mostly neutral/noisy, except MuJoCo Robotiq USD improves by 48% after private lowering. The blocker is API/storage design, not performance.

How a mimic joint should be parameterized in Model

A mimic relation is the scalar affine equation q_follower = offset + multiplier * q_leader. To make it a Newton joint without inflating generalized state, the follower should be a zero-DOF joint that derives its effective coordinate during FK/IK/state transfer.

Reuse existing joint attributes

  • joint_type[j] = JointType.MIMIC marks the row as a derived joint.
  • joint_parent, joint_child, joint_X_p, joint_X_c, joint_label, joint_world, and joint_enabled should be used exactly as for other joints. This is the strongest argument for treating mimics as joints.
  • joint_q_start[j] == joint_q_start[j+1], joint_qd_start[j] == joint_qd_start[j+1], and joint_dof_dim[j] = (0, 0). The follower adds no generalized coordinates, velocities, forces, limits, armature, target, or actuation rows.
  • The leader coordinate should be resolved through the leader joint's existing joint_q_start/joint_qd_start. For the current URDF/USD scalar mimic use case, only scalar revolute and prismatic leaders should be accepted.

Parameters still needed somewhere

Existing per-DOF arrays cannot fully encode a zero-DOF mimic: joint_axis, limits, targets, armature, friction, and effort arrays are all indexed by generalized DOF, and the mimic intentionally has none. Therefore the branch's current joint_mimic_leader, joint_mimic_coef, joint_mimic_type, and joint_mimic_axis arrays are understandable, but they are mimic-specific and dense over joint_count.

The recommended production parameterization is a generic compact relation table rather than mimic-only dense arrays:

  • joint_relation_start[j:j+2]: range of relation rows owned by joint j, usually zero or one.
  • joint_relation_kind[r]: initially AFFINE_COORD; future uses include gear joints, coupled coordinates, tendon-like derived joints, loop closures, or solver lowering metadata.
  • joint_relation_source_joint[r] and optional joint_relation_source_axis[r]: the leader scalar coordinate.
  • joint_relation_coef[r, 0:2]: [offset, multiplier].
  • joint_relation_follower_kind[r] and joint_relation_follower_axis[r]: revolute/prismatic interpretation and axis for the follower transform.

This keeps the topology in the joint list while avoiding attributes that only make sense for JointType.MIMIC. The current branch can be viewed as a prototype of this, with the relation table expanded to one dense row per joint.

Conclusion

Treat mimics as joints only if the production Model stores the dependency generically and compactly. The branch proves the semantic direction is sound: FK, IK, importers, and MuJoCo lowering can operate on zero-DOF follower joints, and Robotiq FK improves by eliminating follower coordinates. But the current dense joint_mimic_* arrays are not the right final API because they are mimic-only and mostly empty on sparse models. My recommendation is: keep JointType.MIMIC, reuse all normal joint topology attributes, replace the dense mimic-specific arrays with a compact generic affine relation table, and continue lowering to solver-specific constraints where native zero-DOF followers are unsupported. If Newton does not want that generic relation table, then keeping mimics as separate constraints is preferable to baking mimic-only arrays into Model.
