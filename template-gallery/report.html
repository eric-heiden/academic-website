Abstract

This report examines whether a Newton physics simulation produces the same numerical result each time it receives the same input. This property is called run-to-run determinism. A simulation state is the complete set of values—such as position, velocity, and orientation—that describes the simulated system at one moment. A solver is the numerical method that advances this state from one step to the next. The study compares repeated runs of three rigid-body solver configurations and one deformable-body case. The rigid-body results remain within the chosen tolerance, which is the maximum difference accepted as equivalent. The deformable-body case, which also measures how outputs respond to input changes, shows a larger difference and requires further analysis.

1. Results

The repeated simulations agree closely until contact introduces a small difference between runs.

Rigid-body simulations are repeatable

Rigid bodies keep a fixed shape while they move. The eXtended Position-Based Dynamics (XPBD), Featherstone articulated-body, and MuJoCo-compatible solver configurations remain below the selected tolerance after 180 simulation steps.

The first contact introduces most of the difference

The largest change between repeated runs appears when objects first touch. The difference then remains limited instead of growing continuously through the rest of the simulation.

The deformable-body gradient needs further analysis

A differentiable simulation also computes how its result changes when an input changes. During this gradient calculation, parallel updates can arrive in a different order and produce a small numerical difference. This case exceeds the strict tolerance and is therefore not classified as deterministic.

2. Numerical difference between repeated runs

The comparison uses the largest absolute difference among all state values at each simulation step.

For simulation step \(t\), the reported difference is

\[\Delta_t = \max_i \left|x_i^{(1)}(t) - x_i^{(2)}(t)\right|.\]

Here, \(\Delta_t\) is the maximum state difference at step \(t\); \(i\) identifies one value in the state; and \(x_i^{(1)}\) and \(x_i^{(2)}\) are that value in the first and second run. Smaller values indicate closer agreement.

4. Newton simulation workflow

The model describes the scene. The current state and control input enter collision detection, then the solver computes the state for the next time step.

5. Reproducibility method

The short implementation below runs the same model with a fixed time step and requests run-to-run deterministic execution.

Listing 1. run_replay.py 
import warp as wp
import newton

current_state = model.state()
next_state = model.state()
control = model.control()
collision = newton.CollisionPipeline(model)
contacts = collision.contacts()
solver = newton.solvers.SolverXPBD(
    model,
    deterministic=wp.DeterministicMode.RUN_TO_RUN,
)

for step in range(180):
    current_state.clear_forces()
    collision.collide(current_state, contacts)
    solver.step(current_state, next_state, control, contacts, 1.0 / 60.0)
    current_state, next_state = next_state, current_state

Reproducibility protocol

In Listing 1, model contains the scene, current_state is the input state for the present step, next_state receives the result, control contains commanded inputs, and contacts stores detected object contacts. Each step advances time by \(1/60\) second.

  1. Start each run independently. This prevents data left by an earlier run from affecting the next one.
  2. Compare the complete state. Check for exact equality first, then measure the numerical difference when values do not match.
  3. Retain visible evidence. Keep a short recording beside the numerical result so unexpected motion can be inspected.

7. Conclusion

The three rigid-body configurations remain within the selected tolerance when the same scene is run independently three times. The deformable-body gradient case does not. The evidence indicates that contact ordering and parallel gradient updates should be examined before that case is classified as deterministic.
