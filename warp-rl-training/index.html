All-Warp RL Training

Can reinforcement-learning training run entirely in NVIDIA Warp, without PyTorch or JAX, and be faster for it? This report covers the Warp extensions that make it practical, a PPO trainer for three MuJoCo Playground tasks, and a FastSAC-style SAC pipeline, both written entirely in Warp. In each trainer, a whole training iteration is a single CUDA graph replay.

All measurements: NVIDIA RTX PRO 6000 Blackwell Server Edition, MIG 1g.24gb partition (46 SMs, about 380 GB/s). Warp 1.20.0.dev on the eric/warp-tensor branch, PyTorch 2.11 (CUDA 13.0), JAX 0.12 (CUDA 13), MuJoCo Warp 4.0.0, MuJoCo Playground 1.0.1, RSL-RL 5.4.2.

What was added to Warp

Warp already compiles Python kernels to CUDA and captures them in CUDA graphs. What it lacked for training neural networks was a fast dense matrix multiply that stays graph-capturable and differentiable, plus a few capture features that whole-iteration graphs need. All changes are on the public eric/warp-tensor branch of a Warp fork, with unit tests and changelog entries.

wp.gemm: cuBLASLt GEMM

cuBLASLt is loaded at runtime (no link-time dependency). Each shape and pointer alignment gets one cached plan, autotuned over the top heuristic candidates on first use. Every call is one kernel launch that can be captured in a graph. It supports fused bias, ReLU and GELU epilogues; backward dGELU and bias-gradient epilogues; batched and strided operands; FP16, BF16, FP32 and FP64; and mixed precision (bf16 operands with fp32 outputs).

Differentiable

wp.gemm records its adjoint GEMMs and bias reduction on wp.Tape. With record_tape=False, a layer can record its own fused backward pass instead.

Runs everywhere

CPU arrays, GPUs without cuBLASLt, and API captures (apic=True) use a built-in Warp kernel with the same arguments, so saved graphs now contain the GEMM instead of silently dropping it. wp.is_cublaslt_available() reports which backend runs, and the cublas-cu12 and cublas-cu13 extras install cuBLASLt.

Capture arenas

ScopedCapture(static_alloc=True) serves allocations made during capture from graph-owned memory instead of graph alloc/free nodes. That makes code that allocates temporaries, such as MuJoCo Warp's forward(), legal inside conditional graph bodies. "Recompute only if some world reset" can then stay on the GPU.

Programmatic dependent launch

With wp.config.enable_pdl, kernels launch with programmatic dependent launch and wait at their start, overlapping each launch with the tail of the previous kernel. The Cartpole simulation step went from 900 to 853 µs with bitwise-identical results. Large kernels and the small SAC networks showed no gain.

Fixes found on the way

Runtime-indexed reads of vector and matrix struct fields now read in place instead of copying the whole value to local memory. FP64 GEMMs on cuBLASLt had been given float scale factors by plans that read doubles; the new tests caught it.

The wp.gemm API
# y = gelu(x @ W + b), keeping the pre-activation z for the backward pass
wp.gemm(x, W, y, bias=b, activation="gelu", aux=z)
# backward through the next layer: dz = (dy @ W2^T) * gelu'(z), with the bias gradient fused
wp.gemm(dy, W2, dz, trans_b=True, activation="gelu", grad_aux=z, bias_grad=db)
# mixed precision: bf16 operands, float32 accumulation and output
wp.gemm(h_bf16, w_bf16, out_fp32)
# differentiable: recorded on the active tape
with wp.Tape() as tape:
    y = wp.gemm(x, W, bias=b)

Tensor workloads against PyTorch

Before building trainers, I measured the basic building blocks against PyTorch. All sides replay CUDA graphs, so launch overhead is excluded. Times are microseconds per call in strict FP32, except the TF32 GEMM.

Where the work is one large GEMM or a bandwidth-bound pass, Warp ties PyTorch: it uses the same cuBLAS kernels and moves the same bytes. The gains come from fusing small networks into one kernel and from training steps without framework overhead (1.14× on the RL policy step). Those are exactly the workloads RL training repeats millions of times.

PPO: MuJoCo Playground in one graph

The MuJoCo Playground trains with PyTorch around MuJoCo Warp, using RSL-RL's PPO. I re-implemented three of its tasks and the PPO trainer in Warp. A whole training iteration then replays as one CUDA graph with no host synchronization: environment steps with physics, observations, rewards and resets, then GAE and every minibatch update. Both pipelines run the same MuJoCo Warp simulator code.

Parity does exactly the PyTorch pipeline's work, including a full simulator forward pass after every auto-reset. Lean recomputes only what the post-reset observations read, and enables programmatic dependent launch.

The gain shrinks as simulation grows. Fewer environments leave more of each iteration to framework overhead, which Warp removes: G1 goes from 2.11× at 1,024 environments to 1.44× at 4,096 (parity). Once the pick-cube gripper holds the cube, MuJoCo Warp's contact solve takes about 1.07 s per iteration in both pipelines, and the speedup falls to 1.10×.

Does it learn the same thing?

The pick-cube port was checked against the PyTorch environment in lockstep, from identical states and actions with noise, delays and randomization turned off. Over 60 control steps, observations agree to 1.2 × 10⁻⁶ and rewards to 4 × 10⁻⁹. Learning curves with the playground's training configurations:

PyTorch: RSL-RL's rolling mean over the last 100 finished episodes. Warp: mean over episodes finished in each 5-iteration window. One seed each. The final pick-cube returns are 185 (PyTorch) and 176 (Warp); a second Warp run reached 167. The G1 gap at iteration 300 is within what one seed can show and not a claim.

SAC against PyTorch and JAX

The second trainer is a minimal version of FastSAC, the SAC recipe for massively parallel simulation from the authors of FastTD3 (code in Holosoma). It is written three times, in Warp, PyTorch and JAX, with the same environment, network shapes, initialization scheme and hyperparameters:

  • Twin Q-networks (768-384-192) and an actor (512-256-128), each hidden layer Linear → LayerNorm → SiLU. A tanh-squashed Gaussian policy with log-std limited to [-5, 0], and automatic entropy tuning.
  • AdamW (learning rate 3 × 10⁻⁴, betas 0.9 and 0.95, weight decay 10⁻³), Polyak averaging with τ = 0.1 after every critic update, and clipped double-Q targets. The distributional critic of FastSAC is left out.
  • Per-environment ring buffers of 1,024 steps and a batch of 8,192. Each iteration is one environment step for every environment, 4 critic updates and 2 actor and temperature updates.
  • A vectorized pendulum swing-up with Gym Pendulum dynamics. With 12 pendulums per environment, observations and actions have robot-like sizes (36 and 12).

In Warp, the iteration is one CUDA graph. The two critics run as one batched ensemble with wp.gemm. LayerNorm and SiLU are fused into one kernel per pass, with hand-written backward passes that match PyTorch autograd to within 5 × 10⁻⁷. Each network has one AdamW kernel and one Polyak kernel over its flat parameter buffer, and the environment step writes straight into the replay buffer. In PyTorch, torch.compile compiles the whole iteration and torch.cuda.graph captures it. In JAX, the whole iteration is one jax.jit with donated state.

Mean return of the 200-step episodes finished in each 200-iteration window, default configuration. All environments run synchronized episodes, so each window holds one episode per environment. About −150 solves the swing-up. All three implementations follow the same curve in both precisions.

Tuning the LayerNorm backward kernel made the batch-1,024 case 1.27× faster: threads per row are matched to the layer width, and blocks are sized to fill the GPU. Before that, JAX was faster there (3.65 ms against 4.27 ms); now Warp leads in all six cases.

What adding this to Warp costs

The native code is small: the cuBLASLt wrapper is a 26 KB object, and the branch's warp.so is 12 KB larger than upstream main built with the same flags. The real cost is cuBLASLt itself. It is optional and loaded only on the first wp.gemm call. Users with PyTorch or a CUDA toolkit already have it; for a PyTorch-free install it is larger than Warp.

Warp already has precedents for optional dependencies:

  • It loads the CUDA driver at runtime and runs CPU-only without it.
  • MathDx is optional at build time, with a runtime probe and generic fallbacks for the tile operations that use it.
  • It has a public wp.is_cubql_available() probe, which wp.is_cublaslt_available() follows.
  • Its pip extras for PyTorch are already split by CUDA major version.

Warp once had a dense GEMM, wp.matmul, built on CUTLASS compiled into the library. It was deprecated in 1.6 and removed in 1.7, together with CUTLASS, in favor of tile primitives. wp.gemm brings a library GEMM back without compiling a GEMM library into Warp. It keeps the same autodiff approach as wp.matmul, with a different signature: an in-place output with beta, explicit transposes, batching, fused epilogues and mixed precision.

Limits and next steps

  • Saved graphs fall back to the slow kernel. API capture records cuBLASLt calls through the built-in kernel. Recording them as native API-capture operations would keep cuBLASLt speed in saved graphs.
  • Contact-heavy simulation dominates. Under contact, MuJoCo Warp's solver and collision detection set the pace for both pipelines; tuning its launch parameters gained at most 6%.
  • Small kernels cost slightly more. A trivial Warp kernel takes about 0.23 µs longer than the same kernel built with nvcc, in the same process and stream. I have not isolated the cause.
  • The SAC benchmark is network-bound. The pendulum environment is cheap, so networks dominate. In a robot task, simulation shares the GPU.
  • Narrow evidence. All results come from one MIG partition, and the learning curves are single seeds.
  • Next: FastSAC's distributional critic and observation normalization, and a MuJoCo Warp robot task for an end-to-end SAC comparison.

Method

Times are steady-state wall-clock per iteration, measured between device synchronizations after warm-up. The SAC comparison runs each framework in its own process: 400 iterations for Warp and PyTorch, and 1,200 for JAX, to get past its slow start. The PPO baselines are the playground's own training scripts with RSL-RL 5.4.2. The tensor workloads replay 20 calls per graph, average over 10 replays, and come from one benchmark session. The Warp trainers run under Warp's default CUDA graph capture; PyTorch's whole-iteration graphs use torch.cuda.graph after warm-up on a side stream.

Warp fork branch: github.com/eric-heiden/warp, eric/warp-tensor. Upstream: NVIDIA Warp. Baselines: MuJoCo Playground, MuJoCo Warp, RSL-RL, FastTD3, Holosoma.
