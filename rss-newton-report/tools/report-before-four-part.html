Newton integration · source audit + hands-on experiments · 7 October 2026 UTC

RoboSimStudio
× Newton

A practical path from RSS’s existing Newton backend to a supported integration.

RoboSimStudio already uses Newton for simulation. The next step is a supported integration: move its viewer customization onto public Newton APIs, keep one owner of simulation state and stepping, and validate cloth interaction, live parameter edits, and recording. The roadmap below turns the existing demonstrations and tests into concrete deliverables and acceptance gates.

01 / Integration strategy

Build a supported RSS companion on Newton’s public APIs.

Recommended integration

Keep RSS independently versioned as the studio application. Use Newton’s model, state, control, solver and viewer interfaces underneath it, and upstream the small reusable interaction capabilities that the integration proves are missing.

Existing foundation

Build on the Newton backend

The recorded RSS scene already combines a robot, rigid objects and a Newton VBD towel. Preserve the working authoring and agent loop while making its dependency and API contracts explicit.

First integration task

Port the viewer customization

Use PR #3850’s public ViewerViser.server interface as the evaluated target. Inventory the remaining private overrides and validate reset, rebuild and disconnect behavior against the pinned Newton revision.

Focused contribution

Validate persistent cloth interaction

Separate patch selection and studio controls from Newton-side force or constraint semantics. Demonstrate the same interaction boundary in RSS and a native Newton example before proposing a core API.

This judgment follows Newton’s requirements for a small public surface, existing abstractions first, explicit units and frames, and consideration of USD for authorable configuration. It is an architecture recommendation, not an exhaustive approval review of PR #3850. Newton coding and API guidelines ↗ Review guidelines ↗

The four-phase roadmap is the proposed work plan. The feature matrix, recordings and test logs establish the starting point; they do not yet establish complete RSS compatibility with the Newton PR.

02 / Integration roadmap

The Newton integration roadmap: compatibility, pilot, APIs, support.

Each phase produces a reviewable integration artifact and advances only when its acceptance gate passes. Durations are rough estimates for a focused effort with the RSS authors, not delivery commitments. The existing tests and videos provide a baseline; the integrated RSS-on-Newton pilot remains to be built.

0

Compatibility spike · roughly 1–2 weeks

Port RSS to the evaluated Newton viewer API.

Rebase RSS’s viewer customization onto PR #3850’s public ViewerViser.server property. Inventory every remaining private call and override, identify which capabilities the PR already supplies, and retain only the customization the studio needs. Run the supplied RSS scene and native Newton panel example on explicitly declared dependency sets. Evaluate the PR’s joint-overlay issue independently before treating this target as supported.

Deliverable: a viewer adaptation patch, a private-API inventory, and a compatibility table tied to exact Newton revisions and test results.

Exit gate: no unexplained private override; reset, rebuild and client disconnect clear stale controls; stable and development compatibility are documented separately. The existing six-probe stable rerun is a smoke test, not full studio certification.

Capability detail: viewer APIs · rendering hooks

1

Newton workflow pilot · roughly 2–4 weeks

Complete one cloth-authoring workflow on Newton.

Prepare the cloth scene, manipulate persistent patches, change a physical parameter, restart from a known state, and record a take with external interventions identified. Exercise the workflow through both studio controls and the local agent session. Queue all mutations onto the application’s simulation thread and invalidate targets when the Newton model is replaced.

Deliverable: a reproducible RSS pilot plus a minimal native Newton consumer of the same interaction boundary, with an explicitly scoped recording or scene artifact.

Exit gate: one owner of model/state/control and stepping; actionable errors; correct failed-edit recovery; intervention-aware recording; and a measured workflow result. The existing recordings establish individual capabilities, while the public API prototype establishes command queuing and stale-command rejection.

Capability detail: simulation ownership · robot controls · cloth interaction · tuning · recording · agent reload

2

Focused Newton contributions · roughly 4–8 weeks, conditional

Upstream the missing interaction and lifecycle primitives.

Use the pilot to select small contributions: particle-patch interaction, reset/rebuild/disconnect hooks, or missing parameter-change notifications and examples. Demonstrate each proposed capability in both RSS and the native Newton example. Keep studio panels, the file watcher, robot presets and experimental engine adapters in independently versioned packages.

Deliverable: small, independently reviewable Newton changes with examples and regression coverage, mapped to the component ownership table.

Exit gate: CPU/CUDA coverage, capture and reset correctness, world isolation where supported, explicit units and frames, declared USD persistence behavior, and a headless import path without studio dependencies.

Capability detail: rigid targets · particle constraints · change notifications

3

Supported integration · after the pilot and API gates

Publish the compatibility and maintenance contract.

Agree which Newton revisions the RSS companion supports, who maintains each package, and which examples and regression checks run in compatibility CI. Document unsupported scene, solver and persistence combinations. Consider closer release coordination or a Newton-organization companion repository once maintainers and users have validated the support model.

Deliverable: a versioned companion release with installation guidance, a support matrix, named maintenance responsibilities and reproducible integration checks.

Exit gate: the declared Newton targets pass the agreed pilot and lifecycle checks. Batched applications and foreign-engine coupling remain separate extensions with their own acceptance evidence.

03 / Newton architecture

Attach the studio to one Newton simulation owner.

The proposed integration keeps RSS’s interaction workflow above Newton’s existing runtime. UI callbacks and agent commands request changes; the application applies them between simulation steps and owns reset, rebuild and resource shutdown. RSS’s high-level scene facade can remain optional while Newton’s native model and solver interfaces remain the integration boundary.

04 / Newton API & USD

Use public Newton APIs and queue changes between steps.

The included prototype uses only public Newton APIs and PR #3850’s ViewerViser.server. A browser callback queues an intent; the simulation thread applies it between steps. A generation number rejects commands that were queued before reset. The same core path runs with ViewerNull. It adds no RSS dependency and proposes no new Newton public class.

# Existing PR API — not a proposed framework
button = viewer.server.gui.add_button("Add upward velocity")
button.on_click(lambda _: commands.put(
    (generation, "kick", 2.0)  # delta velocity [m/s]
))

# In the application-owned simulation loop:
# 1. Drain commands and reject stale generations.
# 2. Mutate state or notify solver / recapture as needed.
# 3. Apply viewer forces, collide, step, then render.

Complete runnable example. CPU and CUDA checks both raised the box by 0.1997 m and discarded a stale command after reset; browser buttons were also exercised.

This small example validates the composition approach. Integrating RSS still requires model-replacement handling, parameter schemas and graph-recapture validation. Those are explicit pilot tasks rather than demonstrated prototype capabilities.

Runtime contract for the RSS–Newton integration

  • One owner: the application owns model/state/control, solver, stepping, reset and resource shutdown.
  • Queued mutation: callbacks submit commands; they do not directly mutate Warp arrays from web threads.
  • Identity: stable object identifiers include the model generation and world/environment, rather than a bare array index that survives a rebuild.
  • Explicit geometry: SI units, named frame, xyzw/wxyz conversion at a documented boundary, and a declared anchor for every placement.
  • Capabilities: unsupported picking, gripper, coupling or sensor behavior raises an actionable error rather than silently degrading.

Lifecycle and performance requirements

  • Clear release behavior: reset, model replacement and client disconnect remove stale interaction targets.
  • Bounded observation: snapshots/readback have a chosen cadence; streaming a panel must not force every environment to synchronize to the CPU every substep.
  • Capture awareness: separate value changes, solver notifications, recapture and structural rebuild; refresh all borrowed handles after replacement.
  • Record interventions: external manipulation is part of episode provenance.
  • Headless remains first-class: importing or running Newton physics must not start servers, load application assets or import optional engines.

USD disposition: reuse physical authoring, keep tasks outside it.

Before adding a new authorable configuration layer, classify what it represents. RSS’s Python scene constructors can remain an optional facade; they should not become another mandatory serialization format for the same physical scene.

Public viewer boundary · Roadmap phase 0

1. Browser controls and a composable viewer API

What it does. RSS puts inspection, camera movement, pause/reset, robot controls and application panels around the same visible simulation. A scene script can add its own readout or control through the page= callback, so the studio can expose a task-specific measurement without requiring a separate web application.

How it works. rss.view(sim) creates the studio session over a built simulation. The session exposes Viser’s GUI and scene objects as studio.gui and studio.scene. Its each_step callback runs on the main thread for control steps the page actually takes; a paused session does not keep invoking it. This gives scripts a place to read state and update widgets. Changes originating in browser callbacks still need to be queued and drained by the simulation owner. Studio API · Session implementation

Why it matters for Newton. PR #3850 already provides much of the basic interaction UI and exposes ViewerViser.server. The integration can compose RSS panels through that public entry point. The remaining task is to remove or justify RSS’s private rendering and lifecycle overrides. The bundled Newton panel prototype demonstrates this composition on CPU and CUDA, including stale-command rejection, without requiring RSS. It is evidence for the API approach, not an already completed RSS port.

Authoring facade and runtime ownership · Roadmap phase 1

2. Named scene construction, state readback and one simulation owner

What it does. RSS reduces a manipulation setup to a cell, a registered robot and named objects. Scene collects construction specifications, scene.build() produces a stepping Sim, and scene.add() returns a Ref for later state access. That makes a short Python scene useful both to a person editing a script and to an agent checking the result.

How it works. The build maps those specifications into the simulation model and its physics arrangement. sim.run(n).sync() advances control steps and then waits for device work; a rigid reference reads pose or velocity from live state. Deformable references expose particle positions instead of a single rigid pose. Names provide an application-level lookup, but model arrays and entity ranges still change on rebuild. A second build rebinds the scene’s references to the new simulation. Scene and reference contract · Builder implementation

Placement and readback use different frames. On bench_075, authored at=(0, 0, 0.2) places the sample box at world (0.6, 0, 0.95); after settling, its center is near z=0.775. A box uses its center as the anchor, a sheet uses an origin corner, and a robot uses its base. The contract probes also show that duplicate rigid names are rejected and the scene has one robot-spec slot, even when that robot is bimanual.

Why it matters for Newton. This is a useful optional authoring layer over Newton. When attached to an existing Newton application, the studio must borrow the application’s model, state, control and step loop. Starting another rss.Sim would create competing owners of time, reset and resources. Generation-tagged commands and explicit world/frame identity keep a queued edit from addressing obsolete arrays.

Robot interaction and metadata · Roadmap phase 1

3. End-effector gizmos, IK and gripper controls

What it does. RSS turns a registered robot into an interactive arm with a target gizmo and a gripper control. A reader can move the hand toward an object, adjust its orientation and open or close the fingers while inspecting the surrounding scene. The value is the packaged connection between robot metadata, controller setup and browser controls.

How it works. Arm panels resolve the relevant arm and tool information, accept target changes from Viser, and apply control updates when the session drains pending requests. Quaternion conversion is explicit at the Viser/control boundary. The arm panel also distinguishes driving the gripper from pinning cloth to a hand frame: the latter imposes an external constraint and does not establish a contact-supported grasp. Arm and cloth panel implementation

Why it matters for Newton. Newton already supplies IK examples and controller building blocks. RSS adds discoverability, defaults and a convenient interaction loop around them. Integration should reuse those APIs and declare the supported arm, end-effector frame, gripper semantics and control mode for each robot. The RSS footage demonstrates gripper controls; the Newton footage demonstrates IK target motion. Neither proves a robot can hold the towel after external pins are released.

Persistent interaction primitive · Roadmap phase 2

4. Rigid handles that keep objects dynamic

What it does. Clicking a rigid object attaches a persistent pose target. Multiple handle slots let the user keep several objects under control, move a linked group, or release selected targets. This supports staging a scene and perturbing an object while it continues to collide with its surroundings.

How it works. ObjectDragger computes a proportional–derivative wrench toward a target position and orientation. It adds that wrench to Newton’s state.body_f rather than replacing the object pose. Stiffness, damping and an acceleration cap govern the response; mass and inertia affect the force/torque calculation. HandleSet manages the browser handles and linked motion, while the object panel registers the force hook with the simulation schedule. These are separate UI and physics responsibilities. Force-based dragger · Handle lifetime and groups

Why it matters for Newton. The reusable piece is a persistent interaction target with clear force, ownership and lifetime semantics. Newton’s transient mouse picking provides related functionality, so integration should evaluate what remains missing before introducing another core abstraction. A persistent drag is also an external intervention: its effect must be represented in recording and cleared across reset, disconnect or model replacement.

Primary Newton interaction pilot · Phase 1 → phase 2

5. Cloth-patch selection, persistent pins and linked manipulation

What it does. RSS lets a user select a patch on a deformable, lift it with a gizmo and leave it held after releasing the mouse. The source also supports multiple handles, linked motion, named particle sets and attachment to a hand frame. Together those operations can prepare folds, expose a contact region or hold an initial condition while another part is adjusted. The study filmed one persistent patch; it did not validate the complete multi-handle workflow.

How it works. The picker resolves a click against the deformable’s particles. ParticleDragger.grab() restricts candidates to the chosen entity, selects particles near the grip point and stores their offsets in the grip frame. The patch retains those offsets as the target moves or rotates. The default dragger caps the patch at 64 particles and uses a 3 cm radius. A scripted caller can disable nearest-particle fallback so a missed grasp returns zero instead of attaching a distant patch. Particle selection and constraints · Cloth panel and hook ordering

The mechanics depend on the mode. A spring adds particle forces before solving. A pin writes particle position and velocity after solving, with a limit on motion per substep. RSS’s cloth panel uses the pin path and registers it in post_solve. “Pin to hand” follows the end-effector kinematically; it does not close the gripper, permit slip or demonstrate a frictional grasp. Foreign-engine deformables require that engine’s own pin interface because its next synchronization can overwrite Newton-side particle edits.

Why it matters for Newton. PR #3850’s rigid-body picking does not supply this patch-manipulation workflow. This is the strongest focused integration candidate: keep hit testing and handle presentation in the studio, and establish explicit Newton-side force/constraint semantics, model identity, solver ordering and cleanup. It must remain clear whether a test uses externally pinned cloth or contact-driven robot manipulation.

from robosimstudio.core.draggers import ParticleDragger

pin = ParticleDragger(model, mode="pin", radius=0.03)
count = pin.grab(state, grip_point, (0, 0, 0, 1),
                 candidates=particle_indices, fallback_nearest=False)
if count == 0:
    raise ValueError("No towel particles within the grip radius")
pin.set_target(target_position, (0, 0, 0, 1))
pin.apply(state, dt)  # Pin mode: on the solved state, after each solver substep
# On release/reset, remove its hook as appropriate and release the target:
pin.release()

Inspectable, graph-aware edits · Phase 1 → phase 2

6. Contextual inspection and live material/solver tuning

What it does. RSS connects scene selection to the controls relevant to that object. A cloth exposes material settings; a rigid entity can expose contact and inertial properties; joint-bearing entities can expose drive parameters. The dedicated Material and Physics panels let a user explore cloth behavior and solver configuration, load or save material presets and see which edits require more expensive work.

How it works. Scene selection resolves to a Subject. The inspector queries the selected entity’s tunables(pipeline); each group provides a specification, field metadata and a writer. Browser callbacks collect pending values; the main-thread drain applies them. The distinction between per-cloth material arrays and model-wide contact scalars matters when more than one cloth is present. Property writers and notifications · Cloth update tiers

Persistent developer workflow · Roadmap phase 1

8. A live agent session that survives failed source edits

What it does. An agent can inspect status, pause, advance a bounded number of steps, edit the scene script and obtain a rendered snapshot while a person keeps the same browser view. Invalid Python does not discard the last working scene. A later valid save replaces the scene while retaining the process and camera, so visual feedback remains available throughout iteration.

How it works. The scene loader executes a file that leaves an rss.Scene bound to scene, then builds it unless the file supplied a sim. An optional BUILD dictionary supplies build arguments. During loading, RSS’s normal viewer-opening functions are suppressed, and the file runs outside __main__, preventing a typical example from opening another server. The watcher tracks the file’s modification time and size; a failed build reports a traceback and keeps the previous loaded scene. File-loading contract · Watcher, swap and commands

The local control channel sends newline-delimited JSON over a Unix socket. The probe pauses the session, requests exactly 12 steps, injects a syntax error, repairs the scene, checks the unchanged process/camera, renders a 640×480 snapshot and restores the original file. The valid reload rebuilds from the scene definition and starts at time zero; it does not preserve the old solver’s dynamic state. The command surface also supports arbitrary local Python evaluation and largely repr-based results, so it is a trusted developer interface rather than a typed multi-user service.

Why it matters for Newton. This is a coherent workflow beyond adding a viewer button. Keep the watcher, local transport and source-edit policy in RSS while making Newton model replacement, disposal, command invalidation and readback reliable. A typed command/result layer would improve automation without expanding Newton into a general agent runtime.

Solver composition and coupling · Newton pilot / later extensions

10. Rigid/deformable solver composition and optional engine bridges

What it does. RSS routes different scene entities to appropriate physics backends while keeping one high-level construction vocabulary. In the documented default arrangement, the robot uses Newton’s MuJoCo backend and rigid objects and cloth use Newton VBD. Optional SuperDex and Genesis paths extend that composition to foreign engines; they are not required for the report’s mixed Newton scene.

How it works. Backend choices group entities into solver islands, and the physics arrangement defines stepping rates, collision handling and coupling between them. The default proxy path allows reaction between the robot and other objects but does not supply the documented full-surface pinch behavior. Full-surface cloth contact uses the one-way path in the inspected configuration, so the cloth responds to the robot without the corresponding reaction on the robot. RSS explicitly rejects the unsupported full-surface/proxy combination. Backend and contact contract · Coupler construction

Foreign-engine bridges run host work outside Newton’s captured graph, mirror rigid motion into the foreign simulation and synchronize particle output back. Feedback is smoothed and capped before it becomes a Newton reaction. The supplied isolated probe reduced a requested 1.666667 N·s impulse to 0.031500 N·s for its 63 g test body. That characterizes shaping in one component; it is not a whole-scene conservation measurement or a benchmark of either optional engine. Host coupling · Feedback shaping

Why it matters for Newton. RSS exposes Newton’s existing multiphysics capabilities through a convenient scene workflow. The integration must preserve solver choice, contact support and the direction of coupling instead of hiding them behind a uniform-looking UI. Keep the first pilot on the demonstrated Newton path; assess foreign-engine bridges through separate numerical and dependency gates.

07 / Integration findings

Five findings that set the Newton acceptance gates.

1

Interactive setup is not a general scene-authoring transaction.

RSS is effective at direct manipulation and source-driven rebuilding. Rebuild-level tuning in a hand-built scene is explicitly redirected to the script; the task-rebuild path depends on the withheld benchmark tier. There is no demonstrated full undo history, persistence of arbitrary UI edits to the source asset, or complete USD round trip. Separate temporary simulation interventions from persistent authoring edits. Apply-and-rebuild implementation ↗

2

The viewer subclass is a maintenance hotspot.

RSS uses viewer._server and overrides or touches internal batching, triangle/particle logging, color synchronization, scene handles, and reset state. The PR’s public viewer.server property removes one important private dependency; it does not make all of RSS’s subclass portable. Phase 0 must identify which overrides can be removed and which need a small public Newton hook. RSS private viewer coupling ↗RSS session ↗

The PR already changes buffer reuse, materials, batching and frame synchronization. Rebase downstream extensions first; do not transplant older RSS optimizations over a newer implementation without profiling equivalent workloads.

3

“One scene” does not imply general multi-robot or batched-world semantics.

The current RSS scene has one robot-spec slot; adding a second robot replaces the first. A registered bimanual robot can occupy that slot, but this is not arbitrary multi-robot composition. Rigid object names reject duplicates. Authoring coordinates also depend on the cell and primitive: box centers, cloth corners, sponge bottom centers, and robot bases are not the same anchor. Readback is world-frame. The probes make these distinctions visible. Scene construction ↗ Characterization tests

4

Coupling quality is not established by a convincing drag video.

The default proxy path can push cloth but cannot provide the same pinch behavior as the full-surface path. The latter is one-way in the documented arrangement, without the corresponding robot reaction; combining full-surface contact with proxy coupling is explicitly unsupported. The documented ADMM choice also carries a failure warning. These are meaningful capability distinctions that must survive a convenience API. Physics and coupling limits ↗ Coupler construction ↗

Foreign-engine coupling runs outside the captured Newton graph, mirrors rigid motion and writes particles back. The feedback accumulator deliberately smooths and caps reaction impulses. In an isolated probe, a requested 1.666667 N·s reaction on a 63 g body became 0.031500 N·s. That is evidence of shaping, not a measured whole-scene conservation error. It may improve interactive stability while changing the physical response. Validate momentum, energy, timestep convergence and contact lag before promoting this into a core coupling API. Host coupling ↗ Feedback shaping ↗ Probe output

5

A take is not automatically an imitation-learning episode.

The recorded take contains 106 samples, an 8-dimensional action vector, robot joints/gripper/EE pose, object poses, timestamps, and privileged body/particle positions. During the take the cube rose approximately 18.4 cm while the action vector stayed nearly constant (maximum component range about 1.6×10⁻⁵). It was moved by a viewer handle. The recorded action channel alone cannot explain the resulting transition.

Before dataset conversion, record intervention type, target, interval and applied command/force, or exclude those intervals from policy demonstrations. Also define rewards and success independently of placeholder fields in a generic scene. The inspected privileged arrays contain positions, not a complete solver checkpoint. Recording source ↗ Take audit · Actual array schema

Dependency and maintenance boundary for the Newton companion

The three shipped Python packages total 237 files and about 67,710 raw lines including docstrings; their tests total about 19,390 lines. This is not a small viewer patch. Base requirements add SciPy, image/video packages, Viser and pinned CoACD alongside Newton. Optional engines bring Python/platform constraints and additional binary stacks. SuperDex is constrained to Python 3.12 in RSS; Genesis brings its own packages; the RTX path targets a particular ovrtx series and private interfaces. None belongs in Newton’s unconditional import/install path. Dependencies ↗

RSS’s main license is Apache-2.0. Robot and other bundled assets have separate provenance and attribution records. If code or assets are selected for upstreaming, review those exact files and preserve required notices; the repository’s main license is not a blanket asset-provenance answer. Notices ↗ Asset provenance ↗

Reuse the Newton Viser front end

Its Python API supplies scene primitives, GUI controls, click/gizmo interaction, camera control and a browser client suitable for remote machines. That lets researchers compose a UI around their simulation without building a separate web application. Newton and RSS already share this substrate. Official Viser documentation ↗

Engineering inference: the shared substrate makes a small common extension surface more economical than a new front end. It also supports a human and an agent observing the same scene.

What Viser does not decide for you

Simulation ownership, physical authoring, persistence, deterministic replay, task semantics and trustworthy sensor images still belong to the application or engine. Browser appearance may differ from sensor rendering. Callback concurrency, client ownership, bandwidth, disconnect cleanup and shared-session permissions require deliberate contracts.

A DOM-driven agent is still interacting with a 3D canvas. RSS’s Python/socket interface is usually the more precise control path. The browser is feedback and shared context.

Agent API assessment: RSS currently offers arbitrary Python eval/exec through a local Unix socket and returns expression values largely as repr. This is an effective trusted local developer tool. A supported remote or multi-tenant service would need a different, typed and permission-scoped contract.
